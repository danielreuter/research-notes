# a100-dumps: the A100 BF16 B-Ligero headline results with their proof bytes in the store (2026-09-22)

fill-a100 ran the three B=4096 B-Ligero modes on an A100 but (a) used `bench_result.py`, a pre-contract emitter whose results
`tables.reject_reasons` rejects on `profile None`, and (b) left the proof dumps on the pod, which is gone. This lane re-ran the three
modes with the contract emitter (`python -m backends.direct.ligero.run bench-vu`, i.e. `backends/direct/ligero/vu.py`) and made the
dumps part of each attempt's `run-files/v1` artifact, so a non-producer can fetch the bytes from the store and verify them. I am the
producer: nothing here is verified beyond the prover's own live Python verifier; no `verified`/`independently_verified` label was
written by this lane. GPU work ran only on vy-a100d through `research run --on`; the laptop launched, pulled, labeled, pushed.

## Spec vs reality

1. **`fetch --all` was not run.** The laptop's disk was at 116 MiB free when I started and 1.4 GiB when the runs finished (other lanes are writing);
   the three trees are 1.44 GB and the store copy had already taken 1.5 GB. The dumps exist in two verified places (local store, R2); a third copy under
   `~/.research/runs/` would have risked filling the disk under every running lane. Records-only `research fetch` for all six runs instead. If the run-dir
   copy is wanted, `research data fetch <run-files art>` reproduces it from the store; the pod is gone.
2. **D7 makes the headline cell unreachable from bytes.** B-Ligero's Table 2 class is `COMPLETE_ZK_BACKEND` = interactive, and the verify lane labels
   interactive dumps `verified=not-transferable` (its report, §4.2: an interactive transcript is live-verifier-only evidence, D7). So even with the coins
   sidecars in the store, r20260922-231224-54dc can be *checked* (transcript consistent with the runner's coins) but not `verified=accepted` under the verify
   lane's vocabulary. The Fiat–Shamir result (r20260922-230823-104f) is the one that can be accepted cold from bytes -- and it is only a drill-down class.
   The spec's "a cell needs a `verified=accepted` label … which requires the proof bytes" is true of the bytes and still not sufficient for the ZK cell.
   Coordinator decision, not mine: an independent live session, or the HVZK cell as the verified headline.
3. **The rebuilt instance root does not carry the frozen manifest** (item 3 above). fill-a100's and every other pod-built `--root` gives `manifest_sha256`
   `db552063…` ≠ frozen `059103cf…`, a second rejection reason for those results besides `profile None`. The v1-frozen root is the fix on the pod side;
   `instances build` could preserve the frozen manifest when the arrays match it, but that is a code change beyond this lane.
4. `bench_vu`'s dump manifest and the result say `commit: null` on a pod (`_git_commit()` in a `git archive`); `bench_result.py` had a workaround
   (`source_commit()` from the `src/<sha>` cwd) that the contract emitter lacks. The attempt's `source.commit` (7754023) is the provenance.
5. This board's A100 is power-limited to 400 W where fill-a100's was 500 W; same SKU by name, 6–9 % slower. If Table 2 wants the best A100 number, the
   board's power limit should be part of the fingerprint (`hardware.gpu` has no `power_limit`).
6. `--dump-dir` inside the run directory did need the code fix (spec: "unless … needs a one-line path fix"): the emitter never listed the dump in `artifacts`
   at all, whatever the path. One helper + one line + a test.
7. The driver's background chain died between runs (the shell session did not keep it alive); the third run was launched by hand 3 min later. No effect on the results.
