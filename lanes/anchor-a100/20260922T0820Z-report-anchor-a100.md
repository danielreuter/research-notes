# anchor-a100: every campaign GPU kernel measured on the A100 (the anchor), 2026-09-22

**Scope: component measurements** (kernel time on random/patterned data, bit-exact against each lane's CPU reference), then one `ARITHMETIC_DIAGNOSTIC` re-price of A and B with those numbers.  Nothing here is a proof except section 7 (the b-ligero torch prover, `NON_ZK_PROOF_DIAGNOSTIC`, verifier-accepted on the A100).  Every recorded 4090 / H100 number is the lane's own (its README / report, run id in the lane's table); every A100 number is a `research run --on vy-a100b --exclusive` of the same bench, same flags, CUDA events, warm, median of >= 7, bit-exact checks on.  `overhead.vs_native_peak` is defined against *this* card's dense BF16 peak (`contract.NATIVE_REFERENCE`, 9.85 ps per K=1536 VU), so the last section is the first A-vs-B comparison where the prover and the reference are the same machine.

Device: NVIDIA A100-SXM4-80GB, 580.126.16, 1410 MHz, 1593 MHz, 81920 MiB; torch 2.6.0+cu124, CUDA 12.4, 108 SMs (sm_80).  Recorded runs: microbench `r20260922-063608-a304`, hash_gpu `r20260922-063811-e561`, encode `r20260922-064413-0508`, fused `r20260922-064953-f9bb`, fused_logup `r20260922-071602-522d`, packed `r20260922-073828-153f`, packed_killed_mislaunch `r20260922-073540-f5b5`, tensor `r20260922-074359-964b`, wave2_gkr (packed Montgomery 2^26, direct 2^28, logUp GKR full-VU) `r20260922-075147-91a5`, wave2_b (b-commit fused commitment + buckets, b-lintest structured linear test) `r20260922-080250-cff5`, ligero (b-ligero torch prover: unit b4096, vu 42, vu 85) `r20260922-081113-f56e`, ligero_failed_attempt `r20260922-080532-9bbb`.

Bandwidth ratios the earlier reports *scaled* by: A100/4090 = 2,039/1,008 = 2.02; A100/H100 = 2,039/3,350 = 0.61.  Speed ratios below are recorded-time / A100-time (> 1 = the A100 is faster); a departure from the bandwidth ratio by > 1.5x either way is a finding about the kernel and is flagged.

**Pattern.**  Only the HBM-bound kernels scale with bandwidth (plain k=0 sumcheck 0.62x the H100, Montgomery packed 0.52-0.61x, batch inversion 1.48x the 4090).  Every INT32-SIMT kernel -- SHA-256, Poseidon2, the SIMT NTT encoder, the fused checker/logUp rounds, the quadratic / linear tests, the fused commitment -- lands near the A100's INT32 issue-rate ratio to the 4090 (108 SMs x 64 lanes x 1.41 GHz / 128 x 64 x 2.52 GHz = **0.47x**), not the 2.02x bandwidth ratio; the 4090 rows that were reported as 'fraction of HBM floor' were ALU-bound kernels on a card with a high ALU:bandwidth ratio.  Blake3 (1.05x) and the launch-bound kernels (logUp GKR 1.04x the H100; the torch INT8-limb round 0.6-1.0x) are card-independent.  Tensor-core kernels reach 4-6% of the A100's INT8 peak (cuBLAS itself only 12%).

**Finding (flagged).**  The SIMT hash kernels do *not* scale with bandwidth: SHA-256 runs at 190 GB/s on the A100 vs 446 on the 4090 (0.43x, where the bandwidth scaling assumed 2.02x -- a 4.7x departure), Poseidon2-16 0.45x, Blake3 1.05x.  They are INT32-ALU-bound: the A100 has 108 SMs x 64 INT32 lanes at 1.41 GHz = 9.7 T int32 op/s against the 4090's 128 x 64 x 2.52 GHz = 20.6 T (0.47x), and SHA-256 / Poseidon2 land on that ratio.  Blake3 holds its rate (its chunk-parallel layout was latency-bound on the 4090).  On the anchor the best proof-internal hash is **blake3 at 377 GB/s** (54.0 ms per B batch, 13.2 us/VU); the note:r20-proof/hash-gpu/20260922T0554Z-report-hash-gpu / notes-asset:campaigns/r20-proof/assets/b-encode/reports/encode_gpu.json A100 rows (SHA-256 x2.02 = 901 GB/s) overstate the A100's hash rate by 2.4x.

## What would not run / caveats

* Nothing was modified for sm_80: every kernel (cupy RawKernels, Triton 3.2 `tl.dot` int8 paths, torch `_int_mm`) compiled and ran bit-exact on the A100 as recorded.
* The fused lane's `tc` variant of the logUp round is not built on any card (`fused_logup` has SIMT only); the fused SIMT logUp round *was* run (section 3b).
* The packed lane's plain k=0 direct 2^28 (140 GB) does not fit the 80 GB card on any GPU; k=2..4 at 2^28 were run (17.8-34.4 GB).
* `cupy` and `blake3` were absent from the pod's venv and were installed (`cupy-cuda12x`, `blake3`); the hash_gpu / encode benches otherwise ran unchanged.
* The A100's `torch._int_mm` reaches 0.12 of the datasheet INT8 peak at 8192^3 (the 4090 got 0.25): the 'fraction of INT8 peak' floors on this card are against a ceiling cuBLAS itself does not approach.
* b-ligero needed `PYTHONPATH=packages/verity/src:backends/numerical/python:.` and `verity_numerical.bench.instances build` on the pod first (the operand arrays are built, not committed); `bench-vu` has no `--vus` flag (85 VUs come from `--batch 8192`).  Run r20260922-080532-9bbb is the failed attempt.
* Model-only rows (`explore.tensor` at 0.172 utilisation) are ESTIMATES; the A vs B section labels every still-modelled bucket.  No proof was produced in this lane except the b-ligero prover runs (section 7, `NON_ZK_PROOF_DIAGNOSTIC`).
