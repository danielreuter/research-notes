# Where the QuickSilver prover spends its time, and what a GPU would change

Companion to `ASSUMPTIONS.md` (the instantiated stack) and `bench.py` (the measurements). Everything in
section 1 is **measured** on `vy-cpu` (AMD EPYC 9655P, 16 vCPU, one dietmc thread, F_{2^61-1}, `lpn = medium`,
swanky `1b05bdda`), runs `r20260922-053217-d21f` (B = 1, 64 VUs; 4096 units) and `r20260922-053613-d110`
(B = 4096 VUs). Section 2 is analysis; every GPU number there is derived from an explicitly stated operation
count and an explicitly stated device rate, never by scaling the CPU wall time.

## 1. The measured profile

`perf` is unavailable inside the pod container (`perf_event_paranoid = 4`, no `CAP_PERFMON`), so the profile
comes from three sources that together account for the wall time:

* dietmc's own timers: `init time` (base OTs, COPEe, base sVOLE, one *setup* LPN extension per field),
  one line per sVOLE extension (`SVOLE<F61p> ... extend time`), and `circ exec time` (parse + evaluate
  the relation, which triggers the extensions on demand);
* the same relation and witness run in dietmc's `--plaintext` mode (parse + clear evaluation only, no MACs,
  no network): the I/O + parsing floor;
* `profile.sh`: gdb stack sampling of the prover (poor-man's profiler), used to attribute the online
  remainder to MAC arithmetic vs. channel I/O.

### 1.1 One relation with 64 VUs (`vu-B64`)

| | seconds | per VU | share |
|---|---|---|---|
| prover wall (RTT-free, localhost through the byte-counting relay) | 25.61 | 0.400 | 100 % |
| `init` (fixed per session; base OT + COPEe + base sVOLE + setup extension, F61p and F2/F40b) | 0.69 | 0.011 | 2.7 % |
| sVOLE extensions, F61p: 103 × (n = 642,048, k = 19,870, t = 2,508 -> 622,178 fresh VOLEs) | 15.96 | 0.249 | 62 % |
| `circ exec` minus extensions = online phase (parse + commit + multiply + checks + I/O) | 8.92 | 0.139 | 35 % |
| ... of which parse + clear evaluation floor (`--plaintext` on the same files) | 4.52 | 0.071 | 18 % |
| ... of which MAC arithmetic, batch checks, channel writes (remainder) | 4.40 | 0.069 | 17 % |
| verifier wall | 26.11 | 0.408 | |
| prover peak RSS 228 MB, verifier 50 MB (both stream the witness/relation) | | | |
| bytes prover -> verifier 549.1 MB; verifier -> prover 69.9 MB | | 8.58 MB / 1.09 MB | |

Per VU the compiled relation (`ASSUMPTIONS.md` section 4) commits 491,702 private wires and 501,393 `@mul`
outputs, i.e. consumes 993,095 VOLE correlations (103 extensions x 622,178 / 64 = 1,001,318 produced; the
rest is the batch-check and field-switch slack), and evaluates ~2.57 M linear gates on MACs. Derived unit costs
at one thread:

* **sVOLE: 249 ns per correlation** (0.155 s per extension of 622k). The extension is (a) t = 2,508 GGM trees
  of 256 leaves (`AES-128` fixed key, ~640k block encryptions), (b) the spsVOLE consistency check (one random
  linear combination over the n outputs), (c) the primal LPN product `y = A u + e` with A a random d = 10-sparse
  n x k matrix over F_{2^61-1}: 6.42 M gathers from a 19,870-element (159 kB) vector and 6.42 M modular
  multiply-adds. At 155 ms, the extension runs at ~24 ns per LPN multiply-add-equivalent: scalar 61-bit
  modular arithmetic with random access, single-threaded.
* **online: 139 ns per committed element** all-in, of which ~70 ns is text parsing + clear evaluation and
  ~69 ns is MAC work. The prover's MAC work per `@mul` is two field products for the QuickSilver pair
  (A_0 = M_a M_b, A_1 = w_a M_b + w_b M_a - M_c), accumulated into the chi-batched check, plus the 8-byte
  `w - u` fix message per committed wire; linear gates are MAC adds.
* **communication: 8.64 B per committed element** prover -> verifier, i.e. 8 B per VOLE consumed plus 0.6 MB of
  batch-check/field-switch traffic per VU. The verifier -> prover 1.09 MB/VU is the sVOLE extension traffic
  (spsVOLE GGM openings and checks; 10.6 kB per extension x 103 / 64) plus the chi challenges.

### 1.3 Instruction profile (callgrind, `profile.sh`, run `r20260922-063937-acf6`)

`perf` and `ptrace` are both unavailable in the container, so the function-level profile is valgrind/callgrind
(exact instruction counts, 25x slowdown) on a dietmc rebuilt without `target-cpu=native` (valgrind 3.15 has no
AVX-512; SSE4.2 + AES-NI + PCLMUL only, `+debuginfo`, `/workspace/target-swanky-prof`). 16 VUs, F61p, one
thread, 64.4 G instructions, bucketed by symbol (`profile_buckets.py`):

| share of instructions | phase / function group |
|---|---|
| 28.5 % | **sVOLE: sampling the sparse LPN matrix's random column indices** (`lpn_mtx_indices`: AES-CTR RNG + `uniform_int` rejection sampling + bounds checks) |
| 21.0 % | sVOLE: the sparse product itself, y = A u + e, F_{2^61-1} multiply-adds (`svole::Sender::send_internal`) |
| 4.1 % | sVOLE: GGM trees / spsVOLE / AES-PRG |
| 19.2 % | parsing the SIEVE-IR text relation and witness (`text_parser`, `BufReader::read_exact`, `consume_byte`) |
| 7.4 % | online QuickSilver: commits, mult-check accumulation, MAC memory (`backend_multifield::Evaluator*`, `homcom::MultCheckState`, `memory`) |
| 12.8 % | F2/F40b side backend (the field-switching backend is always loaded; its GF(2^40) multiply is scalar in this SSE-only build -- production uses PCLMUL/AVX-512 vector paths, so this share is inflated by the profiling build; its wall share from the timers is < 1 %) |
| 3.0 % | libc memcpy / allocator |
| 1.3 % | init: base OT (curve25519), KOS, COPEe, base sVOLE |
| 1.6 % | F61p arithmetic not attributed to a phase |

Read together with the timers (section 1.1: sVOLE 62 % of wall, parse 18 %, MAC work 17 %): the instruction
profile agrees on sVOLE and parse, and shows the online MAC work is *memory-bound* (7 % of instructions for
17 % of the time: streaming 8-byte MACs through `memory.rs` with little arithmetic). Two implementation facts
worth more than any GPU discussion:

* **Half of the sVOLE instructions are spent generating the random sparse matrix, not multiplying by it.**
  Per output, `lpn_mtx_indices` (`svole.rs:117`) draws 10 distinct column indices by rejection sampling
  and 10 random nonzero F_p coefficients from an RNG whose seed both parties coin-toss at init, and it does
  so afresh for every one of the 6,565 extensions (a fresh public matrix each time). Fixing one public
  matrix per session (as Ferret does with its fixed code; the matrix is public either way, so this is a
  security-parameter question about matrix reuse, not a secrecy one) and caching its 6.4 M (index,
  coefficient) pairs (~77 MB) removes ~28 % of the prover's instructions and the same on the verifier --
  a ~1.3x wall win at the cost of an LPN-with-reused-matrix assumption that WYKW21's parameter analysis
  did not consider.
* **A fifth of the instructions parse text.** The flatbuffer IR, or a purpose-built prover taking the witness
  from memory, removes it; `note:r20-proof/c-vole/20260922T0646Z-report-gpu` 2.2 already treats this as a precondition.

### 1.4 The overhead as the ledger counts it

The ledger's native reference is 9.85 ps per VU (one K = 1536 VU at A100 BF16 peak). One prover thread at
0.400 s/VU is an overhead of **4.1e10**; the cost model in `explore/vole.py` predicted ~3e6 on an H100 for a
degree-3-MAC QuickSilver at 2^-128. The 1.3e4 gap decomposes as: ~12x more committed elements than the model
(bits committed as 61-bit field elements, section 4 of `ASSUMPTIONS.md`), ~2.6x more VOLEs per element than
the model's correlation count, single-threaded CPU vs. a whole GPU (~1e3-1e4 in raw arithmetic rate), and
the model's 2^-128 soundness against the measured 2^-61-per-check field. The GPU path below addresses the
third factor only; the first two are relation-compilation questions and are the same for CPU and GPU.

## 2. What a GPU would change

### 2.1 Operation inventory per VU (from the compiled relation, F_{2^61-1}, r = 1)

| stage | operation | count per VU | data touched |
|---|---|---|---|
| sVOLE, GGM | AES-128 block encryptions | 1.6 x 622k/256 x 255 ~ 1.03 M (1.61 extensions/VU) | 8 MB out |
| sVOLE, spsVOLE check | random linear combination over n outputs | 1.0 M mul-adds | 8 MB in |
| sVOLE, LPN | d = 10 sparse gathers + mul-adds from a 159 kB vector | 10.3 M mul-adds | 8 MB out, 159 kB resident |
| commit | `w - u` per private wire, 8 B to the wire | 0.49 M subs | 8 MB out |
| multiply | 2 products + adds per `@mul` (prover); 1 product (verifier) | 1.0 M products | 16 MB in |
| linear gates | MAC adds / scalar muls | 2.57 M | streaming |
| batch check | powers of chi, two length-501k inner products over F_p | 1.0 M mul-adds | 8 MB in |
| zero checks | one random linear combination over 526k asserted wires | 0.53 M mul-adds | 4 MB in |

Total ~17 M F_{2^61-1} multiply-adds and ~60 MB of memory traffic per VU. The CPU does this in 0.33 s of
non-parsing time, i.e. ~20 ns per multiply-add-equivalent: it is not compute-bound in any meaningful sense,
it is single-threaded scalar 61-bit modular arithmetic with gathers.

### 2.2 Which parts are tensor-core matmuls

Honestly: few, and none of the expensive ones.

* **The batch-check inner products** (`sum chi^i A_0,i`, `sum chi^i A_1,i`, and the assert-zero combination)
  are genuine dot products of length 0.5-1 M over F_p. Over limbs (61-bit -> 8 limbs of 8 bits, INT8 tensor
  cores with INT32 accumulate, chunks of <= 2^15 terms before a reduction) they become 8 x L by L x 8 GEMMs,
  ~2.5 M limb-MACs per VU: a few microseconds on an H100's 2 POPS INT8 dense rate. But they are only ~9 % of
  the F_p work; making them free changes little.
* **Dense LPN as GEMM** is exactly what `note:r20-proof/tensor-cost/20260922T0450Z-report-tensor` ruled out: a dense n x k generator over F_p at n = 642k,
  k = 19.9k is 1.3e10 mul-adds per extension (2e10 per VU), 2,000x the sparse count, so the tensor-core rate
  buys nothing against a gather. Dual-LPN (compressing a long sparse-error vector with a dense matrix) has
  the same shape problem.
* **Primal regular-noise LPN is a gather**, d = 10 random reads from a 159 kB vector per output. On a GPU the
  vector sits in shared memory/L1 on every SM; the kernel is 10 loads + 10 61-bit modular mul-adds per
  output, 6.4 M per extension. 64-bit integer multiply is emulated (~4 IMAD.WIDE.U32 + reduction); an H100
  sustains ~1.5e13 IMAD/s over its SMs, giving a floor of ~2-4 us per extension for the arithmetic and
  ~5 us for the 8 MB of writes at 3 TB/s. This is not a matmul; it is a bandwidth- and IMAD-bound SpMV with a
  resident dense operand, and it is ~4 orders of magnitude faster than the measured 155 ms.
* **GGM trees** are 1 M independent AES block encryptions per VU: ~1e12 blocks/s on a GPU with AES via
  bit-sliced/T-table kernels is a microsecond-scale cost. The tree's 256-leaf depth (8 levels) is latency, not
  throughput.
* **Commit / multiply / linear gates** are elementwise streams over 8-byte MACs: pure memory bandwidth,
  60 MB/VU -> 20 us/VU at 3 TB/s; the F_p products (1 M per VU) are ~0.1 us of IMAD time.

So the realistic GPU picture per VU, with the *same relation, same field, same LPN*: sVOLE ~10-20 us,
online ~20-30 us, i.e. **~50 us of device time per VU, an overhead of ~5e6** against the 9.85 ps native
reference, versus 4.1e10 measured on one CPU thread -- if and only if (i) the witness is generated on the
device (no text IR parsing: the 70 ms/VU parse floor is 18 % of today's wall and would be 1,000x the GPU
compute), (ii) the prover is restructured from dietmc's gate-at-a-time streaming into batched kernels
(commit all wires, then multiply all gates, then one check), and (iii) the network is not the bottleneck.
This is the same ~5e6 order that `explore/vole.py` predicted from its correlation counts (3e6 with the
model's 12x fewer committed elements and degree-3 MACs); the agreement is a consistency check on the
arithmetic rates used, not an independent measurement.

### 2.3 The bottleneck that the GPU does not remove: communication

At 8 B per committed element the compiled relation sends **8.58 MB per VU** (13x the 667 kB/VU of the cost
model's **logup** mode, which prices all range and table queries as a logUp lookup argument, 306 VOLEs per
unit, and has output-free boolean checks; the compiled relation commits 4,254 range-check bits and 610 lookup
selectors per unit as full 61-bit elements and pays one extra committed wire per `b^2 = b`, section 4 of
`ASSUMPTIONS.md`). At B = 4096 VUs that is 35 GB per batch. On a 25 Gb/s link that is 11 s -- already 200x the ~50 us/VU
device budget (0.2 s per 4096 VUs). A GPU prover at 5e6 overhead is therefore communication-bound by two
orders of magnitude, on a datacenter link, before AntMan or any packing. The three levers, in order of
leverage:

1. **Relation compilation**: drop the committed output of every `b^2 = b` (4,864 of 10,343 VOLEs per unit are
   there only because the IR's `@mul` has an output wire; QuickSilver's check needs none -- a `@assert_zero`
   of a degree-2 form, which the IR cannot express without a plugin), commit bits in F_2 with field switching
   (dietmc supports F2/F40b and the Diet Mac'n'Cheese conversion gadgets) so a range-check bit costs one bit of
   VOLE rather than 8 bytes, or realise range and table checks as a logUp-style lookup argument (the model's
   306 VOLEs per unit for all of them; no VOLE tool ships one). Together these are the model's 12x, on
   communication and on VOLE count, CPU and GPU alike; they change the compiled relation, not the checker,
   and belong to the exporter.
2. **Larger field, fewer checks**: F128p (2^-97 per VU-batch soundness, section 1 of `ASSUMPTIONS.md`)
   doubles bytes per element; going the other way, no prime-field extension MACs exist in dietmc, so
   F61p's 2^-61 per check cannot be amplified without changing the tool.
3. **AntMan-style SIMD** (section 6 of the brief; opened only after this profile): amortises the per-element
   fix message across B copies of the same circuit, which is exactly our shape (4096 identical units per
   step). What it buys at our measured 8.58 MB/VU, and what machinery it adds, is the subject of `note:r20-proof/c-vole/20260922T0620Z-report-antman`
   if that stage is reached.

### 2.4 What I did not do

* No GPU was available to the lane (vy-cpu has none); every number in 2.2 is an operation count divided by a
  published device rate and should be read as a floor for the device time, not a prediction of wall time.
* The CPU number was not scaled by "cores x SIMD" to obtain a GPU number.
* dietmc's multithreaded mode (`threads = k`, one sVOLE instance per thread, one TCP connection each) is a
  CPU-parallelism measurement, reported in `ASSUMPTIONS.md`/the ledger separately where run; it does not
  change the per-VU work.
