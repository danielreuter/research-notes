## What exists today (corrects the proposal's picture of our area)

- PoUW's Python is `verity/protocols/accounting/work/pouw/` (about 100 files): `protocol.py`, `audit.py`, `window.py`,
  `coins.py` (epoch coins v1), `identifier.py` (v1), `serving.py`, `schemes/` (NCP, Pearl FP8, Pearl-C, Pearl-C4 and
  variants), `circuit/` (pc8, pc4, rowk, cap, ncp2, leaves, hashes, anchors, partition, plan, reference) and pinned vectors.
- PoUW's Lean is already in the Security package: `verity/Security/Definitions/Pouw`, `Specs/Pouw/{Assumptions,Guarantees}`
  and `Proofs/Pouw/{PearlC,NCP,Fp8Atom,Dimension,Barrier,TileBound}`. There is `Specs/` (Assumptions + Guarantees), not
  `Properties/`; renaming it is a move, under `audit.py --update --moved`.
- Every PoUW guarantee is about a model (`Protocol Q R S`, `HiddenAudit`, `Workload`), not about code that runs.
  No PoUW property names an executable `Pouw.verify`, because none exists. Under "a property names the code it's about",
  nothing PoUW proves today qualifies yet.
- The verdict that served windows rely on is Python (`window.py`, `audit.py`, `benchmarks/pouw/pearl_c_vllm/window.sh`).
  In the hidden-tile path, the per-tile verdict is already Lean (`flock-verify`, `backends/flock/verifier/lean`, with SHA-512
  in `Flock/Hash.lean` and no `@[extern]`).
- `benchmarks/pouw/` holds much code under test: kernels (`kernels`, `pearl_c_sm120`, `nvfp4_sm120`, `pouw_hash`),
  the statement staging (`served_zk/stage_tile.py`, `hidden_zk/`), the serve and window drivers (`served_zk/serve.sh`,
  `pearl_c_vllm/window.sh`) and `e2e_audit.py`.
- PoUW's timed rows need GPUs: window.sh's interleaved stock-FP8 / Pearl-C / no-hash / BF16 panel takes the whole of
  node 2 (8 GPUs, clocks locked at 2100 MHz, `gpu-lease 8 --wait --timed`; kernel-engineering skill tier 2b). The
  proposal's quiet nodes read as CPU nodes, and its GPU node group is "later, from node 1".

## 1. Where PoUW goes

- `core/protocols/pouw`: an executable `Pouw.verify`, plus a refinement proof to today's model, so the model-level
  guarantees become properties `@[about Pouw.verify]`. The hidden-tile verifier is the first realistic target, because it
  recomputes nothing in FP8. It is the draw (randomness), SHA-512 openings against the registered roots (the window's tile
  tree and the -h3 tile tree) and `flock-verify` per drawn tile, all of which is Lean already.
  The open sampled path (bit-exact tile recompute) follows. It needs executable Lean FP8/sm_120 semantics, and these
  exist only as Definitions today.
- `core/primitives`: the formats PoUW's prover and verifier share: identifier v1, epoch coins v1, the leaf and tile-tree
  hashes (`PouwPc8LeafH3_v2`), and the tile-check Program's digest.
- `Security/`: the existing `Definitions/Pouw`, `Specs/Pouw` → `Properties/Pouw`, `Proofs/Pouw`, unchanged except for the
  move.
- `experimental/`: `window.py`, `audit.py`, `schemes/`, `protocol.py`, until `Pouw.verify` lands.
- `ml/`: kernels (already the top-level `kernels/`), `serving.py` and the vLLM hook (or `integrations/vllm`), statement
  staging (`stage_tile.py`, `hidden_zk`), and the circuit builders (`circuit/*.py`), as producers of core's formats.
- `benchmarks/pouw`: the timed panel, its inputs, the stock-FP8 / BF16 references, the correctness check (bit-exact verdicts)
  and the overhead ratio. `gamma.py` stays as the metric that reads Lean's γ formula.

Wrong side of the core/ml line: the tile-check Program and the bit-exact tensor-core semantics it encodes. The proposal
puts both under `ml/circuits` (`ops/`, `silicon/`). For PoUW they are the verifier's reference: the hidden verdict accepts
a tile because the Flock proof shows that the tile-check Program holds on the committed rows (L3 in
`Specs/Pouw/Assumptions/PearlC/HiddenTile.lean`). A changed Program changes soundness, not just speed or completeness.
`silicon/` may keep the hardware captures and the evidence that a GPU matches the semantics (that's completeness).
The semantics themselves, and the Program digest the verifier pins, are core.

No home: Python twins of core's formats. The prover (ml/) must compute exactly the bytes that core's Lean checks. ml/
can't import Lean, so each format needs a Python twin pinned to core by vectors (our `*_vectors.json` today). Name the
place and the rule: twins live in ml/, and their vectors are generated by core's executable.

## 2. Rules that would stop, slow or break PoUW

- **"Code under test runs in its own process and touches neither the timer nor the store."** PoUW's overhead ratio comes
  from interleaving stock-FP8, Pearl-C, no-hash and BF16 in one process with CUDA events, which cancels clock and thermal
  drift. Separate processes widen the confidence interval and lose interleaving. Change to: the harness owns the clock,
  and it may time in-process through its own library (CUDA events). The code under test can't read or write the timer
  or the record.
- **"Retention: whatever a ref points to is kept"** covers store objects only. Last night's loss (note:
  compute-accounting/20261006T2334Z-friction-stale-delete-step-outran-keep) was about 28 GB of node-local passes cited by a
  run and never uploaded. A PoUW window's passes are about 27 GB, and whether to upload them is with Daniel. Change to:
  a run either uploads what it cites, or declares a node-local output, which the cluster keeps until the citing ref is
  dropped. The keep records (#1420) and `retention rm`'s refusal (#1418) are the interim form.
- **"A property names the code it's about"**, with nothing else citable. Until `Pouw.verify` exists, every PoUW table row
  loses its guarantee citation. Proposed: model-level guarantees stay citable as their own proof class ("model") until the
  executable and its refinement land, and they are marked as model-level in tables.
- **"Computational assumptions are reductions"** hits one of ours. C6 `PearlCSem.RowDrawn` (`TTOutRowSeed.lean`) takes an
  injective key, which idealizes the row leaf's collision resistance; it holds only because Q is abstract. Only the skip
  class's fragment corollary (`ttOutRowSeed_skipClass`) reads it, not P2's main line. It is to be restated as a reduction
  (any violation yields a SHA-512 collision), or dropped. The S0 bridge's "binding" hypothesis should be written as a
  reduction from the start.
- **"Timed runs wait in their own Kueue queue"** needs a quiet GPU node. PoUW's timed panel needs node 2's 8 GPUs, with
  root to lock clocks (`nvidia-smi -lgc`), so the quiet pod must be privileged. Serve (vLLM, hours, untimed) needs the same
  GPUs, and serve isn't "a service with exclusive cores".
- **"Shared lists are one file per entry"** should cover `lean-audit.json`: the guarantee pins and `reads_exempt` sit in
  one file that every parallel Lean PR edits.
- **"Hidden inputs come from a seed fixed after the commit"**: for PoUW, that seed must be only the source of the protocol's
  own coins (`derive`, epoch coins v1), never a replacement for them, or the benchmark measures a different protocol.

## 3. The quiet nodes and the re-timing test, for PoUW

PoUW's reference row is window.sh's tier-2b timed panel on node 2. The re-timing test for PoUW runs that panel twice:
once in a privileged whole-node pod under Kueue with locked clocks, and once on bare metal under `gpu-lease 8 --timed`,
on the same commit and inputs. It passes when the Pearl-C / stock-FP8 ratio and the per-variant times agree within their
confidence intervals. Our quantities are millisecond kernel times and ratios, so we're less exposed to microsecond jitter
than PoUS's 854 µs window. The sign-off risk is GPU access and clock control, not jitter. compute-accounting signs off on
retiring `gpu-lease` when that passes, and when serve has a GPU home that doesn't block the timed queue.

## 4. One most important change

Put the verifier's reference in core/: the tile-check Program (by digest, with its Lean meaning) and the bit-exact
tensor-core semantics it encodes. Without that, "ml/ affects only speed and completeness" is false for PoUW, because an
ml/ circuit change changes what the hidden-tile proof proves.
