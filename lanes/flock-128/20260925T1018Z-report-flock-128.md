# flock-128: a Flock (b684b12) profile at 2^-128 under TABLES accounting, and what it costs

## Summary
- **Today's profile, with no credit for grinding:** `Fast` is 2^-110.0 per whole proof with live verifier coins, and
  2^-50.0 under Fiat-Shamir (x2^60 state restoration). The ~2^-100 figure used earlier was a rough estimate. Under the
  same rules, the F128 PIOP sites alone sum to 2^-118.4, so no single-run GF(2^128) profile can reach 2^-128.
- **flock-128-r2 (implemented):** two sequential runs of b684b12 `Fast100`, each with its own transcript domain and its
  own live verifier coins, with no credit for grinding. That gives 2^-195.5 for the CPU union (2^-196.1 at m30) and
  about 2^-194.6 for the GPU pair (the unit proof plus the BLAKE3 proof). Flock's code is unmodified; the change is
  parameters plus a harness. Under Fiat-Shamir, neither r2 nor any repetition reaches 2^-128: (2^60 x 2^-97.8)^2 = 2^-75.6.
- **Cost at 4096 VUs (r2 vs today's `Fast`, same pod, every proof verified, every negative rejected):**
  CPU union 2.00x prove (BF16) and 1.93-1.94x (FP8), the same on the cpu3g pod and on the H100 pod's host; H100
  Flock-CUDA pair 1.00x (BF16) and 0.91x (FP8). Proofs are
  1.98-2.00x larger, and verify takes 1.5-1.8x as long. The H100 comes out at or below 1x because Flock-CUDA's
  grinding, which `Fast100` turns off, costs about 0.11-0.16 s per proof: as much as a second proof.
- **flock-128-f256 (paper only):** one run with every F128 PIOP and batching site moved to GF(2^256). It still needs
  live coins. I estimate 1.5-1.7x prover cost, but it changes the protocol field, so it is not implemented.

## Method
- **Site census.** `evidence/pod-scripts/site_census.rs` wraps the `Challenger` trait and logs every squeeze with its
  call site, on 8 shapes: hopper BF16 and E4M3, at 1024 and 4096 VUs, under Fast and Fast100
  (`evidence/census/*.tsv`). `evidence/accounting.py` assigns each site its Schwartz-Zippel degree and takes the
  Ligerito terms from the embedded TOML schedules (`evidence/configs/`). Run it as
  `accounting.py census/<f>.tsv configs/m<m>_<profile>.toml --reps 2`.
- **Accounting rules (TABLES).** The bound is for the whole proof. PoW and grinding get no credit. Only proven bounds
  are used: BCH+25 list decoding in the Johnson regime with eta 0.02, and F256 MCA. Fiat-Shamir costs x2^60 on every
  statistical term (B-Ligero PROTOCOL §8c); live verifier coins avoid that factor.
- **Cost runs.** Each benchmark is the same one earlier lanes ran:
  - CPU: one union proof of the census unit plus the BLAKE3 row leaves, using flock-bench-80gb's `unit_shape.rs`
    extended as `unit_shape128.rs` (`evidence/flock-128-r2-cpu-harness.patch`).
  - GPU: two Flock-CUDA proofs on the H100 (sm_90, CUDA 13.3 with compat): the unit, through flock-bench's
    host-witness port, and BLAKE3. The patch is `evidence/flock-128-r2-gpu.patch`, generated by
    `pod-scripts/g128_patch.py`.
  - Both profiles run on the same pod. CPU runs alternate profiles within one process (5 runs each). GPU runs
    alternate profiles across 2 rounds x 3 runs per shape.
  - Prove time for r2 is the sum of the two sequential reps. GPU prove time includes the host glue and the witness
    upload but not host witness generation, as in flock-bench-80gb.

## flock-128-r2 parameter set
- Flock b684b12, crates unmodified. `PcsParams { m, profile: LigeritoProfile::Fast100, log_inv_rate: 1,
  log_batch_size: embedded initial_k (6 for m30-m33), num_lanes: union.commit_lanes(batch) (CPU) or None (CUDA),
  merkle_hash: Default (CPU) or Sha256 (CUDA) }`.
- `reps = 2`. Each rep is a full independent proof over the same statement and witness, in transcript domain
  `flock-128/fast100x2/rep{0,1}`. The verifier accepts only if both reps verify, and it fixes the profile itself.
- **Live coins are required.** The cost runs use FsChallenger with a per-rep domain as a stand-in; the prover does the
  same work either way. The 2^-195.5 figure needs a `Challenger` that takes every squeeze from the live verifier, as
  the campaign's live-verifier sessions do for B-Ligero.

### Negatives (all rejected)
- CPU, both profiles, 4 shapes:
  - rep0's proof replayed as rep1 (`Zerocheck(CEvalMismatch)`, or an `InvalidGrindingNonce` under Fast);
  - one byte of rep1 flipped (`PcsOpen(Ligerito)`);
  - rep0 verified under the other Ligerito profile (`PcsOpen(Ligerito)`);
  - one witness bit flipped in rep0 (`Zerocheck(SumcheckFinalFailed)`).
- GPU, both profiles:
  - replay as rep1 (`Zerocheck(CEvalMismatch)`);
  - yr[0] flipped (`PcsAb(Ligerito)`);
  - a zerocheck round flipped (`SumcheckFinalFailed`, or `InvalidGrindingNonce` under Fast);
  - the other profile (`BadGrindingNonceCount`);
  - an invalid unit witness, on both reps (`Lincheck(ConsistencyFailed)`).

## What a Flock red team must audit (inputs for red-team-flock)
1. **The live-coin protocol.** The sequential-repetition lemma: the error multiplies across reps under independent live
   coins, and does not under FS. Independence of the reps (separate domains, fresh coins). The forwarding `Challenger`
   the live verifier needs (not built).
2. **The 7 fixed inner zerocheck coordinates** (N_INNER, univariate skip with K_SKIP=6). The eq point uses a
   protocol-fixed prefix; a cited lemma must show the fixed prefix loses no soundness.
3. **The degree of each site** (`evidence/accounting.py`): multipoint gamma (degree K-1), the univariate-skip degrees,
   lincheck degree 63, the jagged degree-255 site, the Merkle-shift degree-3 rounds, and the ring switch in F128^7.
4. **Ligerito proximity:** BCH+25 Johnson-regime list decoding at eta 0.02, the subfield descent for split
   commitments, the F256 MCA term a/2^256, and the union over the claim and consistency lists (L_max).
5. **Two-point OOD binding** in the list regime.
6. **The Fast100 schedules.** The m30-m33 TOMLs are frozen and their raw `expected_eps_*` values must match the
   ledger. The verifier must derive the profile itself (the downgrade negative passes; audit that it is enforced).
7. **Hashes.** The CPU prover uses a custom chained-BLAKE3 challenger and BLAKE3 Merkle trees; Flock-CUDA uses
   SHA-256 for both (`CUDA_HASH`). Soundness under live coins does not rest on the transcript hash, but binding
   does. Table 1 must name which hash each line uses.
8. **GPU and CPU equality.** Flock-CUDA's transcript and schedule (`FlockCudaProveParams`, which carries 0 for an
   absent grinding site) must match the Rust verifier squeeze for squeeze under Fast100 as well as Fast. The Fast100
   roundtrips verify, which is evidence but not an audit.
9. **The union registry and padding contract** for the CPU union proof (how the unit and BLAKE3 tables are padded and
   bound), and the m30 padding of the FP8 1024-VU unit on the GPU.
10. **Out of scope here:** link conditions C1 and C2, and the chain glue C4 (red-team-link).
