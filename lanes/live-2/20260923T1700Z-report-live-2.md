## 0. Design (before measuring)

Where the ~2x live tax inside `t.total` (dev-h100-2 §2: bf16-hopper 0.665 s live vs 0.27-0.31 s local at 30-38 ms RTT,
`--batch 16384 --pipeline 4`) can come from, reading the pipelined live path (`live.ProverSession.start_pipeline` +
`pipeline.prove_many`):

1. `ProverSession.provide_tests` / `provide_stmt` / `_send_root` call `sendall` on the DRIVER thread (the one thread that
   launches kernels), under `_send_lock`.  A bf16-hopper l=16384 sub-batch's TESTS frame is ~1-2 MB and its STMT ~1 MB; the
   pods' effective `SO_SNDBUF` is the kernel's `wmem_max` cap (unknown inside the container, typically 208 KB, not the 8 MB
   asked for), so `sendall` returns only when most of the message has been ACKed over the 30 ms path -- tens of ms per
   sub-batch on the compute path, counted as prover time (not as `net_idle`: the driver is "busy").
2. The reader thread sends ROOT/STMT from the boxes INLINE (`_send_root` on COMMIT), also under `_send_lock` -- while it is
   blocked in that `sendall` it reads no OPEN1/OPEN2, and the driver's `provide_tests` blocks on the lock behind it.
3. `set_statement` builds the statement bytes on the driver thread inside the pass (`starter`); local coins skip it.
4. `submit()` serialises the proof (`proof_bytes`, 3.7-7.8 MB) on the calling thread; in the pipelined path that is after the
   pass (outside `t.total`), in the sequential path inside the rep.

Fix: one ctrl SENDER thread per session with a FIFO queue; the driver and the reader only enqueue (STMT j, ROOT j, TESTS j in
8c order per sub-batch; boxes drained by the reader into the queue, never sent inline); the round-trip clock starts when the
sender hands the frame to the kernel; the statement is built on `pipeline.POOL` and resolved by the sender; the proof is
serialised on the data-sender thread.  Diagnostics added to `net.*` evidence: `ctrl_send_seconds`, `ctrl_queue_seconds`,
`proof_serialize_seconds`, effective `sndbuf`.

Depth-2 pathology (dev-h100-2 §2, 27-28 s sessions, opening RTT p90 2.3-2.6 s = RTO back-off shape): reproduce first on the
same tree (e0cf2cd) against the EU-SE-1 verifier with `ss -tin` sampled on both ends, then with the sender fix.

Ligerito challenge stream: generic `challenge(label, message, n)` per batch; the verifier commits ALL R coins of a batch at once
(one CCOM frame, R x 32 B) -- 8c's commit-then-open kept per BATCH, not per round: per-round commitments (COMMIT k+1 riding on
OPEN k) add nothing to soundness/ZK (each coin is still committed before the prover message it answers) but couple the wire
order of consecutive rounds, which is exactly what windowing across batches wants to relax; per-batch commit lets the verifier
commit W batches ahead as today.  Synthetic 50-round bench at real RTT, window 1/4/8.

## 2. What was built (54345d3)

1. **`live.ProverSession` ctrl SENDER thread** (`_ctrl_send_loop`): the only writer of the control socket while a pipeline
   runs.  `provide_stmt / provide_root / provide_tests` (driver thread) and the reader's COMMIT handling only enqueue; STMT j /
   ROOT j / TESTS j keep 8c's per-sub-batch order (FIFO; STMT j and ROOT j are queued together on COMMIT j); the opening's
   round-trip clock starts when the sender hands the frame to the kernel.  The statement bytes are built on `pipeline.POOL`
   (`live.set_statement` submits a Future when the session is pipelined; the sender resolves it), and `submit()` no longer
   serialises the proof on the caller's thread (`proof_bytes` runs on the data-sender thread).  `_send_lock` is gone.
   New `net.*` evidence per session: `ctrl_send_seconds`, `ctrl_queue_seconds`, `proof_serialize_seconds`, `sndbuf` (the
   EFFECTIVE SO_SNDBUF), `tcp_cc`.
2. **`vu.py --pipeline N`** (the Ampere BF16 cell path, `--relation bf16`): `ChainRunner._prove_stages` (public vectors +
   torch hints inside the stage, `hints_host` timed inside the prover's clock as `prove_arrays` reports it) and
   `ChainRunner.prove_arrays_many` (-> `pipeline.prove_many`, slots warmed in rep 0 like relchain's), used by `bench_vu` for
   recorded reps when depth > 1 on CUDA; `--auth included` supported (the AuthStatement is built in the starter); with
   `--verifier` the coins are `live.LiveCoins` with the non-blocking futures and HELLO window = depth.  Requires the torch
   hint generator.  `run.py` help updated; the result's backend block records `pipeline`.
3. **Many-round challenge stream** (for Ligerito): frames CCOM i / MSG i k / CHAL i k, `ChallengeSession` (sender + reader
   thread), `ChallengeStream` (per batch: `begin / challenge / challenge_future / commitments / openings`), `LocalChallenges`
   (same interface, no network), `ChallengeServerSession` (served by the same `live serve`; HELLO `proto = "challenge-stream"`),
   `expand_challenge` (SHAKE-256 over tag | H(stmt, all commitments) | k | label | r_k), `live chalbench` (the synthetic

Findings from this pass (the design in §0 was HALF right):

- **The sender was not on the compute path on this pod**: `sndbuf` = 16 MB (this kernel's wmem_max is large), so the old
  inline `sendall` never blocked; the new sender's `ctrl_send_seconds` is 0.06 s per session and `ctrl_queue_seconds`
  0.01 s.  Accordingly `t.total` did not move (fp8-ada 0.392 -> 0.391).  On a pod whose wmem_max is the usual 208 KB the
  inline sendall WOULD have blocked (~2 MB frames at 45 ms RTT = tens of ms per sub-batch on the driver thread) -- the
  `sndbuf` evidence field now tells which case a run was in; dev-h100-2's pod is unknown.
- **Where the ~2x inside t.total comes from**: lost overlap, not blocking.  `t.total` = pass wall minus the intervals where
  EVERY sub-batch in flight waits on the verifier (`pipeline.net_idle`).  A bf16-hopper sub-batch is ~11 ms of overlapped
  prover work at depth 4 (0.28 s / 25) but >= 2 x 45 ms of round trips + ~50 ms of transfer (3 MB of STMT + TESTS at
  530 Mbps) = ~140 ms of network; with only 4 in flight, most of the time 3 wait and 1 computes ALONE -- its host work no
  longer hides under another sub-batch's device work, so the per-sub-batch prover time doubles and is correctly counted
  as prover time.  The tax is the pipeline running at effective depth ~1 while the network holds the other slots.  Deeper
  windows (depth 8: 1.2 GB/slot) halve it; the honest fix for the METRIC is to report t.total from the local-coins control
  (prover-only) and t.total_live from the live run, which the runners already do.
- **The 25-42 s bf16-hopper sessions (dev-h100-2's "depth-2 pathology") reproduce at depth 4 here (2 of 3 reps of the
  base tree; 1 of 3 of the new tree was the same shape)** -- it is not depth-specific.  `ss -tin` sampled every 0.25 s on
  BOTH ends during a 3-rep run (`ss_diag2*.log`): the CONTROL connections lost 0-189 segments per session; the DATA
  connections (the 120 MB proof stream, sent after the pass) lost **1000-1400 segments per session**, cubic's cwnd fell
  from 11500 segments (16 MB in flight against a 3 MB BDP) to **1-9 segments**, `pacing_rate` 1-20 Mbps, and one 120 MB
  transfer took > 90 s; the verifier's Recv-Q stayed small (its reader keeps up).  The path drops line-rate bursts; every
  ctrl round trip during a lossy transfer queues behind it (RTT medians 100-200 ms at 45 ms RTT), and when the loss hits
  the application-limited ctrl stream (a tail after every TESTS frame: nothing to trigger fast retransmit) the opening
  waits for an RTO (250 ms) with exponential back-off -- the p90 of 2.3-3.3 s.  Depth 2 is simply the depth at which one
  RTO-stalled opening idles the whole pipeline (depth 4 hides one, depth 1 has no competing burst).
  Fix under test: **bbr on the DATA connection** (`LIVE_TCP_CC_DATA`, default `bbr`; paces at the bandwidth estimate, no
  cwnd collapse), ctrl stays cubic (live-verifier's finding); alternative knob `LIVE_PACING_MBPS` = SO_MAX_PACING_RATE.

## For ligerito-design

Measured 18:50-18:54Z, 4090 EU-RO-1 -> live verifier EU-CZ-1 (`live-verifier@54345d359ac9`, `live chalbench`), the synthetic
many-round protocol: **32 batches x 50 rounds**, 4 KB prover message per round, 32 challenge bytes per round, no simulated
prover compute (pure protocol latency), `window` = batches in flight (that many prover threads; rounds strictly sequential
within a batch); every session ACCEPTED by the verifier (its wire checks: committed batch, STMT first, rounds 0..49 in order,
each once).  Path RTT during the run 26-35 ms at best (the probe an hour earlier said 45 ms; the path varies).

| bbr | 4 | 1767 / 1873 ms | 34.5 / 37.4 ms | 2.24 | 14.3 s |

Local honest verifier (same code path, no network): 50 rounds in ~1 ms per batch (hashing only).  Raw JSON:
`/workspace/results/chal/chal50_{bbr,cubic}.json` (stored, see §7); the verifier's per-round records are in its session dirs
(`c2026...-xxxx/session.json`: every round's label, message digest, receive time, the opened coins).

What the numbers say:

- **A batch costs R x RTT of latency whatever the window** (50 x 26-35 ms = 1.3-1.8 s here): rounds are inherently
  sequential.  The window buys throughput almost linearly until the path or the verifier's session thread saturates:
  0.27-0.71 -> 1.6-2.2 -> 3-4.3 batches/s at W = 1 / 4 / 8.  For Ligerito this means the interactive live-verified mode
  is a THROUGHPUT mode: with W batches in flight the prover's per-batch work (ms) hides under the RTT chain, but a single
  batch can never finish in less than R x RTT -- at 50 rounds and a same-continent verifier that is ~1.5-2 s per proof,
  ~10x the prover's own time.  A Fiat-Shamir Ligerito has no such floor; an interactive one wants R small (fold more per
  round) or W large (many proofs per session).
- **The small-message regime is bbr's bad case** (live-verifier's finding, reproduced): at W = 1 a 4 KB message per round
  costs 65 ms under bbr vs 26 ms under cubic (bbr paces a flow that never has enough in flight to learn the bandwidth); at
  W = 4-8 the flow carries enough that bbr is at the RTT (33-35 ms) while cubic starts queueing (51 ms at W = 8).  For a
  many-round protocol with SMALL messages, `LIVE_TCP_CC=cubic` at W <= 4; for big messages (a Ligerito round that ships MBs
  of openings) bbr, for the reason in §4 (cubic's loss collapse).  The prover picks per session; the wire is the same.
- Commit-per-BATCH (CCOM i = all R commitments up front) is what makes W independent of R: the verifier commits W batches
  ahead and nothing in round k of batch i waits on anything of batch i+1.  Argument in `live.py`'s challenge-stream
  comment: per-batch fixes every coin before the prover's FIRST message (the verifier provably cannot adapt coin k to
  messages 0..k-1 -- the simulator gets the whole tape at once), per-round (COMMIT k+1 riding on CHAL k, the literal 8c
  shape) is sound but strictly weaker and couples consecutive rounds on the wire; cost of per-batch is R x 32 B (1.6 KB at
  R = 50) up front, nothing on the critical path; per-round buys nothing back (one RTT per round either way).

## Interface

What `ligerito-proto`'s `transcript.LiveCoins` should call (all in `backends/direct/ligero/live.py`, 54345d3+):

~~~python
sess = live.ChallengeSession(host, port, hello: dict, n_batches: int, rounds: int, window: int = 1)
#   one control connection; HELLO {"proto": "challenge-stream", "n_batches", "rounds", "window", ...hello}; a sender thread
#   and a reader thread own the socket; the verifier commits `window` batches ahead (CCOM i = R commitments, 32 B each).

st = sess.stream(i)                                   # -> live.ChallengeStream, batch i (0-based, in order)
st.begin(statement: bytes) -> None                    # STMT i: the public claim, fixed before any coin of i is opened
st.challenge(label: bytes, message: bytes, n: int) -> bytes
#   round k (k counts the calls, 0..rounds-1): sends MSG i k = (label, message), waits for CHAL i k = (r_k, s_k), checks
#   coin_commit(r_k, s_k) == the k-th commitment of CCOM i (LiveError "verifier equivocation" otherwise), returns
#   expand_challenge(ctx_i, k, label, r_k, n) = SHAKE-256(b"ligero-chal|v1|" | ctx_i | k | len(label) | label | r_k)[:n]
#   with ctx_i = blake2b(b"ligero-chal-ctx|" | len(stmt) | stmt | c_0 .. c_{R-1}).  BLOCKING (the sequential prover).
st.challenge_future(label, message, n) -> concurrent.futures.Future[bytes]
#   the same, non-blocking: yield it from a stage generator to pipeline.prove_many (it has .net = True, so the driver
#   books the wait as network idle); resolves to the challenge bytes or raises.
st.commitments() -> list[bytes]                       # the R commitments (for the transcript / the verifier's record)
st.openings()    -> list[tuple[bytes, bytes]]         # (r_k, s_k) of every round opened so far
st.latency       -> float | None                      # begin() -> last challenge (seconds); st.rtts, st.wait

v = sess.end(summary: dict | None = None) -> dict     # END; the verifier's VERDICT {"accepted", "complete_batches", ...}

live.LocalChallenges(rounds, batch=0)                 # the honest verifier played locally: same begin / challenge /
                                                      # challenge_future (-> None) / commitments / openings / latency
~~~

Rules the verifier enforces (a violation is an ERROR frame that fails every pending future of the session): a message
names a COMMITTED batch (i < committed); STMT i before MSG i 0, once; MSG i k for k = the next round of i, each once, k < R;
END after the last CHAL.  The proof of a batch travels on the data connection as today (not exercised by the synthetic
bench).  Server: `python -m backends.direct.ligero.live serve ...` (the same process serves 8c sessions and challenge
streams; HELLO "proto" selects).  Bench: `live chalbench --verifier tcp://H:P --rounds 50 --batches 32 --window 1,4,8
[--msg-bytes 4096] [--compute-ms 0] [--local-control] [--out x.json]`.
