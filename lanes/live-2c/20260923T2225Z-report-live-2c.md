### 6.4 What each clock is, and what the table reports

* `t.total` (every run): the prover's own time, prover + hints, median over reps. In a live pipelined run it is the pass
  wall MINUS the intervals where every in-flight sub-batch waits on the verifier; it still contains the lost overlap (a
  sub-batch computing alone while the others wait on the network), so a live run's t.total is 1.0-1.1x the local control
  same-DC, 1.5-1.8x at 30 ms, 1.8-2.5x at 111 ms.
* `t.total_live` (live runs only; measurement in the result JSON, per session in `evidence.live_verifier.per_rep`) =
  t.total + the median network wait = the pass wall from first launch to last proof produced, network idle included.
  Never below t.total (contract check).
* Neither clock contains: the proof stream after the pass (107 / 195 MB per 4096-VU session), END, and the verifier's
  verdict (its Rust verify: 2.3-5.4 s same-DC on RO) -- the rep line's `pass wall` has those; it is not a prover number.
* `tables.py` Table 2 prints **t.total only** (cell = min t.total over the VALID results of the candidate on that device,
  R_proved = 2KB / t.total); t.total_live appears nowhere in the tables. The footnote's verification note names the verifier:
  a live-verifier-accepted interactive run reads "accepted by the LIVE verifier ... (D7)"; a local-coins run "verified
  against the runner's step-0 coins (not transferable per D7)".
* **Recommendation**: per device, two runs on the same pod, same tree, minutes apart: (a) local coins = the prover-only
  t.total for the cell; (b) live against RO = the D7 evidence (accepted by the live verifier with its own coins) and the
  `t.total_live` column, quoted with its RTT and `prover_dc -> verifier_dc` (both are in the rep line and the evidence).
  Same-DC (b)'s own t.total is within 1.0-1.1x of (a), so if a device gets one run, make it (b) with the prover in EU-RO-1.
  Cross-region, never put (b)'s t.total in the cell (the table would pick (a)'s anyway: min t.total).
