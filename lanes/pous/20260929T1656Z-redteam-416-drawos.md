  - `upstream.watch` gains `A3-uniform-bytes`.
- **`drawOS_subset_escape_le`, `drawOS_stratified_escape_le` and `drawOS_work_escape_le`.**
  - They are about `runOS`: the same `drawWith` code, run on the model source `tapeGet`, which fails on any read past a
    stream's tape.
  - Over a source A3 makes uniform, a run that finishes and misses B has probability at most `Law.subset`'s or
    `Law.stratified`'s escape, for every tape length L. A run that reads past its tape counts as no escape, which is
    the safe direction.
- **The extend-and-rerun loop is really analysed.** `onWith`'s `repeat` loop is unfolded in `StateT (ℕ → ℕ) Option`
  through core's `Lean.Loop.forIn_eq_of_monadTail`, with an invariant (`loop_inv`). `subset_append` makes a rerun after
  success change nothing.
- **`execOS_escape_le` and `execOS_subset_escape_le`** state the same as a `Law`: a run-out draws every unit, which is
  conservative. So they compose with audit theorems; #418's `audit_window_of_le` takes exactly their form.
- **Non-vacuous:** A3 holds for Ω = the tapes and t = id.
- **Still open, as the PR says:** the unbounded run's escape is the limit over L, and that step is argued in prose.
  - I agree with the argument. The runs that finish within L bytes a stream increase to all finishing runs, each is
    bounded, and a run that never finishes draws nothing to accept.
  - It is a measure-theory step, not a Lean fact, and it's documented as such.
- **Optional:** no law form of the *work* draw is pinned; `execOS` at `.work` has only the probability form,
  `drawOS_work_escape_le`. It's a three-line corollary through `execOS_escape_le_of`, if a work draw ever needs
  `audit_window_of_le` through `drawOS`.

## 2. A3 (`uniform/io-getrandombytes`): granted as a named hypothesis

- **The statement is right.** `UniformRandomBytes L t` says t's pushforward is the uniform measure on independent
  uniform bytes. It is a `Prop` taken as `ht`, never an `axiom`, and it is satisfiable, so no theorem taking it is
  vacuous. It's registered in `verity.claims` (standing `standard`) and in `ASSUMPTIONS.md`.
- **`drawOS_def` ties it to the verifier as far as Lean can.**
  - The `rfl` pins that `drawOS` is literally `drawWith` with every stream's bytes from `IO.getRandomBytes`.
  - `Flock.Draw`'s definitions are now in the pins' reads, so any edit to `drawOS`, `drawWith`, `onWith` or
    `stratifiedWith` moves a record.
  - Nothing there escapes unfolding (no `implemented_by`, `extern`, `partial` or `opaque`, which `audit.py`'s `escapes`
    check would catch), so the verifier runs the definition `drawOS_def` names.
- **What `rfl` can't show** is that the `IO` run returns what the model run returns on the bytes the calls deliver. That
  step rests on `drawWith` being generic in its monad, together with A3. Please say this in one sentence in A3's text:
  today it says only that "the theorems are about `drawWith`".
- **A3 promises more than Lean's declaration does.** This is not a condition.
  - Lean v4.34.0's docstring says `IO.getRandomBytes` "is not guaranteed to be cryptographically secure".
  - Its runtime (`lean_io_get_random_bytes`, `src/runtime/io.cpp` at v4.34.0) reads `/dev/urandom` until the buffer is
    full on Unix, and uses `BCryptGenRandom` with the system-preferred RNG on Windows.
  - So on the verifier's hosts A3 is the kernel CSPRNG, the standard assumption. That's what grounds the `standard`
    standing, and A3's text should cite that implementation beside the disclaimer.
  - A3 idealizes the CSPRNG as exactly uniform. The true bound carries the CSPRNG's negligible distinguishing
    advantage, as every OS-randomness assumption does.
- **The watch entry can't see the C implementation.**
  - `audit.py`'s `upstream` check fails only when a fetched dependency proves a theorem mentioning `IO.getRandomBytes`.
  - A toolchain bump that changed `lean_io_get_random_bytes` would pass it, because the Lean side is an opaque
    extern.
  - Suggestion: add "re-read `lean_io_get_random_bytes`" to the toolchain-bump steps. The `dependencies` check already
    stops at every bump, so that is the natural moment.

## 3. The refactor: at `IO`, the same calls in the same order

- **By inspection:**
  - `onWith` is `onOS`: read `need` bytes, run the sampler, and on failure append `need` more and rerun. `return none`
    after the loop replaces an unreachable `throw`, which `drawOS` now makes instead.
  - The subset and Bernoulli branches use stream 0 with the same `need` expressions.
  - `stratifiedWith` visits strata in array order (`for i in [0:strata.size]`, then `strata[i]!`), one `onWith` per
    stratum, then the same `qsort`.
  - `WorkStratum` extends `Stratum`, so the old work loop's `need`, `k`, `size` and `unit` were already
    `toStratum`'s.
  - `get` ignores the stream index at `IO`.
  - `drawOn`, the given-bytes path, and `Main.lean` are untouched, and no reference to `onOS` remains.
- **The differential test.** I transcribed #412's `onOS`/`drawOS` and ran them against #416's path on the same logging
  byte source, over 1,200 random subset, Bernoulli, stratified and work laws.
  - The source returns all-`0xFF` chunks on 0%, 30%, 60% or 90% of calls, so the samplers reject.
  - That gave 7,257 source calls, 5,089 of them extend-and-rerun extensions.
  - The call sequences and the draws matched with 0 mismatches.

## 4. POUS's correction to my #412 note: accepted

- At both `da1e703a` and `8aed7908`, `flock-verify draw` without `--stream` calls `Draw.drawOS`, which extends and reruns
  and never refuses.
