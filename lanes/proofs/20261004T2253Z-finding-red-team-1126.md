# Red-team review of PR #1126: circuit-check cache v2 (per-target keys)

PR: https://github.com/danielreuter/verity/pull/1126, branch `cursor/circuit-check-target-keys-8c79`, head
`363d03b1fd8f398cb2fc714e6ee0e31ebf16f902`, base `06edf032c`. Evidence (the real-tree probe and its log, the failing tests,
the suite logs): `art:162fcdacf26320526a291d8c2b87a38c90ddede7938c1ad715f2bff6a92d8443`.

## Verdict: SHIP-WITH-FIXES (two required fixes, both small)

The PR claims that a cache hit means everything this target's check read or resolved is unchanged. That claim fails for one
realistic edit the not-covered list doesn't name. When a kernel is added for a target that had none, the cache keeps the
target's old pass, even though a fresh run fails `correspondence/kernel-mismatch`. I reproduced this on the real tree, not
only in a synthetic test. Separately, two `_model_roots` entries with one label share one unit, so an edit to the first
reaches no key. No duplicate exists today. Both fixes are small, listed under "Required fixes". Everything else I probed is
either on the not-covered list, unreachable from circuit-check today, or a hardening nit. With the two fixes in, the cache is
fit to gate `check`.

No `review` label is applied, because the verdict is not SHIP.

## Q1, Q2: false hits

### H1 (unlisted, realistic): a kernel registered for a target that had none

The edit: add a kernel for an existing Definition that has no kernel yet. In the real tree that means a `_row(...)` call in
`verity_vllm/program/kernels/rows.py` (44 `_row(` sites today), a new `ir_rows.FAMILIES` entry, or a `register_kernel` call in
any kernel module.

Why the key misses it:

- `correspondence` looks the target up in `verity.evaluation.batch._KERNELS` (`kernels(t)`, batch.py:74–75; `_pick`, :78–81).
  The lookup is a dict read, and the cache records only file reads, listings, probes, libraries, executed code and pins.
- If the lookup finds nothing, no kernel code runs, so the target's frame holds no line of the module that would register
  one.
- That module ran at import, under `targets.load_registries()`, so it is attributed only through the static import closure of
  the target's roots (`attributed`, `_top_imports`). Kernel modules register themselves into core (`register_kernel`), and
  nothing the target imports imports them back. So the module is never in the closure.
- A pin's absence is recorded (`recorded_pins` records `kind#key` even when the key is missing). A kernel's absence is not.

Compare `ir_lower.PIECES`: it has the same lookup-by-key shape, but `ir_lower.py` imports `tail_pieces` at top level (:95),
so a target that runs `ir_lower` holds `tail_pieces.py` through `_top_imports`. The hole is specific to registries filled by
modules that the registry's owner never imports. Here that is `_KERNELS`, and through it
`verity_vllm.program.kernels.kernel_registry` (its `register` calls core's `register_kernel`).

Listed? No. It isn't C-extension I/O, isn't outside the repository, and isn't data opened at import. `rows.py` is code, and
no target's check reads it. It isn't a process-wide cache returning another target's value; the absence is this target's
own. It isn't a `targets.py` binding, and it isn't a Definition mutated in place.

How likely real edits trigger it: high. Adding a numpy row kernel for a family is the ordinary vLLM workflow. Many targets
qualify: my enumeration of the suite (1654 targets, `find_targets.py` in the art) found at least 40 vLLM registry targets with
no kernel, and that list is capped at 40. Two examples are `GeluTanhMulBf16_v1` (dense.py) and `F32ExpRn_v1`. The core
suite's every-kernel test covers only kernels defined in `verity` modules (`tests/evaluation/test_evaluation.py:78–81`), so
for a vLLM kernel, circuit-check's correspondence is the self-check against the reference. I found no other suite that
self-checks every vLLM kernel. Packs (`tools/check/verdicts.py`) carry entries between machines, so a stale entry also
travels.

Real-tree reproduction (`real_probe.sh` in the art): on the PR head, run `circuit-check --all --cache`, restricted to two
targets, from the source tree with 0 untraced. The steps are a cold run, then this append to
`integrations/vllm/verity_vllm/program/kernels/dense_rows.py`, then a run under a fresh cache and a run under the first cache:

### H2 (unlisted, latent): two `_model_roots` entries with one label

The edit: change the first of two `_model_roots` entries that share a label.

Why the key misses it: `_units_of` (cache.py:492–531) names each entry's unit `_model_roots:<label>` and assigns it in a
dict (:512–514), so the second entry's digest overwrites the first. Meanwhile `targets.catalog` runs both entries
(targets.py:623–629), each under the same unit name. A target made by the first entry holds a unit whose digest covers only
the second entry. `_model_list` (:471–480) checks the entries' shape but not that labels are unique.
(`TEMPLATE_PARAMS` doesn't have this problem: in a dict literal only the last duplicate key is live, and only it is
digested.)

Listed? No. The PR's "an edit to a binding that doesn't reach the target" covers edits outside the target's units. This one
is inside the target's own unit, which is computed wrongly.

How likely real edits trigger it: low today. There are 75 labels and no duplicates, and nothing enforces uniqueness. A
copy-pasted entry is the realistic way in, and when it happens the false hit is silent.

Tests:

- `test_an_edit_to_either_of_two_same_label_entries_changes_a_unit` (a unit-level check on `_units_of`). It FAILS with
  `an edit to the first Dup_v1 entry changed no unit: every target that holds it keeps its key`.
- `test_an_edit_to_the_first_of_two_same_label_entries_reruns_what_it_made` (end to end). Flipping `make(False)` to
  `make(True)` changes SynMade_v1's value at (5, 3) from [2] to [65534], not its id. It FAILS with
  `SynMade_v1 reused its entry (value [2]) where a fresh run computes [65534]`.

### Probed and not a hole (or listed)

- `verity.ml.boolean.mufu._fits()` (`@cache`, mufu.py:114) reads `verity/ml/tables/mufu_quadratic.json` through
  `importlib.resources`, and no digest of it is pinned in source. Once one target in a worker has loaded it, later targets
  get the cached dict and don't hold the JSON. This is on the list (process-wide caches, data opened before tracing).
  Likelihood: medium-low, since a refit of MUFU coefficients is rare, but when it happens it edits only that JSON, and the
  Boolean lowerings and their pins depend on it. I did not measure how many real targets miss the file. A cheap hardening
  would be a sha256 of the JSON in `mufu.py`, checked at load, which is the pattern `_decoded` already follows.
- `verity.ml.mufu._decoded` (`@lru_cache`, .xz tables): listed. It's mitigated because the tables are checked against the
  sha512 in `library.py`, so changing a table means editing a source file that every user of it holds.
- C++ twins (`twins._tc_lib`, `cpu_model.lib()`; `.so` files under `$VERITY_NUMERICS_BUILD_DIR` or the XDG cache, outside the
  tree): listed. They're mitigated by `_jit.source_digest()` reading `cpp/*` in the module's import frame, which a target
  holds when it runs that module.
- `functools` caches and memo dicts (`reference._CALLS`, `word._RULE_CACHE` and `_RULES`): `_tasks` gives each traced check a
  fresh memo. `_RULE_CACHE` is enabled only by the manifest CLI. What remains is listed (process-wide caches).
- Lazy imports, `importlib.import_module` and `pkgutil` (`load_registries`): the wrapped `__import__` and `import_module`
  plus `_MODULES` frames attribute them. I found no gap beyond H1.
- `sys.monitoring`: `recording()` restarts events, so code that an earlier target ran and `DISABLE`d is seen again. I found
  no gap.
- The `common`/AST split: apart from H2, an edit lands in exactly one unit or in `common`, and `common` covers every module
  statement outside the cut-out units.
- `pins.json` enumeration: `recorded_pins` records `kind#key`, `kind#*` or `*`, including a missing key. Nit:
  `recorded_pins.__getitem__` on a missing kind records nothing. No check path uses it (`_counts_against_pin` uses
  `.get(kind, {}).get(key)`).
- Definitions with equal ids, `made_by` and `producing`: binding-made Definitions are attributed to their units through
  `_MADE` and `_PRODUCED`. Mutating a Definition in place while keeping its id is on the list. Apart from H2 I found no
  realistic way in.
- `check.py`'s key and cache sharing: the key holds `sys.version`, platform (system, machine, libc), the distributions hash,
  and the `VERITY_*`/`CIRCUIT_CHECK_*` environment. `check` also passes `FLOCK_*` (and `UV_`, `LC_`, `XDG_`) but they aren't
  in the key. No circuit-check path I found reads `FLOCK_*` (a nit). The cache directory
  `~/.cache/verity-check/circuit-check` is shared per machine under that key, and packs move entries between machines. That
  amplifies any false hit, which is one more reason the H1 fix is required.
- `os.fork` is not in `UNTRACEABLE` (cache.py:72). A check that forks would read things in the child unseen. Nothing on a
  circuit-check path forks today (`word.prefetch` forks but circuit-check doesn't call it). This is hardening: add
  `"os.fork"`.
- `visible()`: files git doesn't track count as absent, so a read of a gitignored file (a generated or fetched file inside
  the tree) is never keyed on its content. I didn't find a circuit-check target that reads one. The docstring should say this
  outright, beside "outside the repository".
- `boolean_export._patch()` wraps `IL.PIECES` for the whole process, so state depends on which target ran first in a worker.
  That is process-wide state, which is listed. I found no verdict that depends on it.

## Q3: is the not-covered set too weak to gate `check`?

No, apart from H1. Each listed exclusion is unreachable from a circuit-check path today, mitigated by a digest pinned in
source, or rare:

- C-extension I/O: the `.so` twins are mitigated through `cpp/*`.
- Outside the repository: the build directory, and the mitigation is the same.
- Data opened at import, and process-wide caches: the `.xz` tables are pinned by sha512. `mufu_quadratic.json` is the one
  realistic exposure, and it's rare.
- Bindings that don't reach the target: that's the design.
- In-place mutation of a Definition: I found no instance.

H1 is not on the list and lies on a common workflow, so the PR's claim is false as stated until it's fixed. H2 is latent, and
its fix is one line.

## Required fixes

1. Kernel lookups as inputs. Instrument `verity.evaluation.batch.kernels` and `_pick` the way pins are instrumented, so the
   current frame records `kernels#<key_of(target)>`. Its digest, recomputed at lookup from the live `_KERNELS` (the lookup
   process has loaded the registries to build the catalog), covers the sorted kernel names plus each fn's `co_filename` and
   `co_firstlineno`. An added, removed or moved kernel then changes the key, and an edit to the body of an existing kernel is
   already held because its code ran. A coarser option that is also sound: record the calling module of every
   `register_kernel`, and have any check that consults the registry hold all of them. `test_a_kernel_registered_in_a_module_no_check_ran_reruns_its_target`
   is the regression test.
2. Unique `_model_roots` labels. `_model_list` returns `None` when labels repeat (the whole function then becomes one unit,
   which is sound), or `targets.py`'s suite asserts unique labels. Either of the two H2 tests is the regression test.

Optional: add `os.fork` to `UNTRACEABLE`. Pin `mufu_quadratic.json` by sha256 in `mufu.py`. Have the docstring name
"files git doesn't track" among the exclusions.

## The red-team tests (`tools/circuit_check/tests/test_cache_redteam.py`; also in the art)

```python
"""Red-team probes of `circuit_check.cache` v2 (PR #1126): edits that change a target's verdict while its key stays the same.

Each test states the property a sound cache keeps (an edit that changes the verdict reruns the target), on the synthetic tree
of `test_cache`: a cold run, the edit, a run under a fresh cache (the verdict as it is now), and a run under the first cache.
A test fails where the cached run reuses the stale entry."""
from __future__ import annotations

import json
import subprocess
import sys
from pathlib import Path

from test_cache import FILES, HARNESS, REPO, _edit, _entry

#: the real correspondence check (the reference, `kernels` and `self_check`), not `test_cache`'s stand-in
CHECK_CORR = """
def check_definition(fn, opts, *, memo, pins, as_call=None, **kw):
    from circuit_check import checks as CK
    from verity.evaluation.reference import resolve

    F = CK.Findings()
    corr, _arrays, _ref = CK.correspondence(resolve(fn), opts, F)
    return {"failures": F.failures, "warnings": F.warnings, "realizations": corr["realizations"]}
"""

#: a kernel module of the kind `verity_vllm.program.kernels.rows` is: imported with the registries (`load_registries`), before
#: any check, registering kernels for Definitions defined elsewhere
KERN = """
import numpy as np

from verity.evaluation import register_kernel

register_kernel("SynAdd_v1", lambda a, b: ((a.astype(np.uint64) + b) & 0xFFFF, None))
"""


def _harness(registries: str, check: str) -> str:
    h = HARNESS.replace("import syn.extra, syn.idle, syn.kdef, syn.other, syn.top", f"import {registries}")
    h = h.replace("from syn import catalog, check\n", f"from syn import catalog\nfrom syn import {check} as check\n")
    return h.replace('print(json.dumps({"stats"',
                     'print(json.dumps({"targets": {t["target"]: {k: t.get(k) for k in ("failures", "value")} for t in rep["targets"]}, "stats"')


def _tree(tmp: Path, extra: dict[str, str]) -> Path:
    subprocess.run(["git", "init", "-q", str(tmp)], check=True)
    for rel, text in {**FILES, **extra}.items():
        p = tmp / rel
        p.parent.mkdir(parents=True, exist_ok=True)
        p.write_text(text.lstrip("\n"))
    return tmp


def _run(root: Path, harness: str, cache: str = "cache") -> dict:
    """``cache`` other than the tree's own: a directory beside the tree, which no listing of the tree sees."""
    where = 'root / "cache"' if cache == "cache" else f'Path({str(root.parent / f"{root.name}-{cache}")!r})'
    h = harness.replace('cache=root / "cache"', f"cache={where}")
    r = subprocess.run([sys.executable, "-c", h, str(root), str(REPO)], capture_output=True, text=True, cwd=REPO)
    assert r.returncode == 0, r.stderr
    out = json.loads(r.stdout.strip().splitlines()[-1])
    assert not out["stats"]["untraced"] and not out["stats"]["errors"] and not out["stats"]["changed"], out
    return out


def _codes(fails: list[dict]) -> list[str]:
    return sorted(f"{f['check']}/{f['code']}" for f in fails)


def test_a_kernel_registered_in_a_module_no_check_ran_reruns_its_target(tmp_path):
    """`kernels(t)` finds nothing for SynTop_v1, so its check runs none of `syn/kern.py` and its key holds no file of it.  A
    kernel registered there afterwards (as `rows.py`'s `_row(...)` or a new `ir_rows.FAMILIES` entry registers one) is
    `self_check`ed on a fresh run, and a wrong one fails `correspondence/kernel-mismatch`."""
    root = _tree(tmp_path, {"syn/kern.py": KERN, "syn/check2.py": CHECK_CORR})
    h = _harness("syn.extra, syn.idle, syn.kdef, syn.other, syn.top, syn.kern", "check2")
    cold = _run(root, h)
    assert cold["stats"]["stored"] == 2 and cold["targets"]["SynTop_v1"]["failures"] == []
    assert "syn/kern.py" not in _entry(root, "SynTop_v1")["reads"]["files"]
    (root / "syn/kern.py").write_text((root / "syn/kern.py").read_text()
                                      + 'register_kernel("SynTop_v1", lambda a, b: ((a.astype(np.uint64) - b) & 0xFFFF, None))\n')
    fresh = _run(root, h, cache="fresh")
    assert _codes(fresh["targets"]["SynTop_v1"]["failures"]) == ["correspondence/kernel-mismatch"]
    warm = _run(root, h)
    assert "SynTop_v1" not in warm["hits"], (
        f"SynTop_v1 reused its entry (failures {warm['targets']['SynTop_v1']['failures']}) for a correspondence/kernel-mismatch")


#: `targets.py` with two `_model_roots` entries of one label
DUP_TARGETS = """
def _model_roots():
    return [
        ("SynOther_v1", lambda: "SynOther_v1"),
        ("Dup_v1", lambda: "first"),
        ("Dup_v1", lambda: "second"),
    ]
"""


def test_an_edit_to_either_of_two_same_label_entries_changes_a_unit():
    """`_units_of` keys each `_model_roots` entry by its label, so of two entries with one label only the last is digested,
    though `catalog` runs both (each under that one unit, `_produce`)."""
    from circuit_check import cache as CC

    units = CC._units_of(DUP_TARGETS.lstrip("\n"))[0]
    edited = CC._units_of(DUP_TARGETS.lstrip("\n").replace('lambda: "first"', 'lambda: "edited"'))[0]
    assert edited != units, "an edit to the first Dup_v1 entry changed no unit: every target that holds it keeps its key"


#: a Definition whose body depends on what the binding passed, not on its id (`make(swap)`), over a primitive that does not commute
MINUS = """
from verity.ir import Value, composite, primitive

V = Value(16)


@primitive("SynMinus", 1, [("a", V), ("b", V)], V)
def SynMinus(a, b):
    return (a - b) & 0xFFFF


def make(swap):
    @composite("SynMade", 1, [], lambda S: ((("a", V), ("b", V)), V))
    def SynMade(B, S, a, b):
        return B.call(SynMinus, b, a) if swap else B.call(SynMinus, a, b)
    return SynMade
"""

#: the catalog's `_model_roots`, two entries labelled alike, run by the harness as `targets.catalog` runs them
DUP_CATALOG_TARGETS = """
def _model_roots():
    from verity.ir.defs import bind
    from syn import minus, other
    return [
        ("Dup_v1", lambda: bind(minus.make(False))),
        ("Dup_v1", lambda: bind(other.SynOther)),
    ]
"""

CHECK_EVAL = """
def check_definition(fn, opts, *, memo, pins, as_call=None, **kw):
    from verity.evaluation import evaluate
    return {"failures": [], "warnings": [], "value": list(evaluate(fn, 5, 3))}
"""

RUN_ENTRIES = """
import runpy
T = runpy.run_path(str(root / "targets.py"))
ENTRIES = [((f"_model_roots:{label}",), (lambda make=make: [make()])) for label, make in T["_model_roots"]()]
for units, make in ENTRIES:"""


def test_an_edit_to_the_first_of_two_same_label_entries_reruns_what_it_made(tmp_path):
    """The first `Dup_v1` entry makes SynMade_v1 with ``swap=False``.  Flipping it to ``True`` changes SynMade's body (its
    value at (5, 3): 2 -> 0xfffe), not its id, and changes only the first entry, which no unit digests."""
    root = _tree(tmp_path, {"syn/minus.py": MINUS, "syn/check3.py": CHECK_EVAL, "targets.py": DUP_CATALOG_TARGETS})
    h = _harness("syn.other", "check3").replace("for units, make in catalog.BINDINGS:", RUN_ENTRIES)
    h = h.replace("if TG.family(fn) in catalog.FAMILIES:", 'if TG.family(fn) in ("SynMade_v1", "SynOther_v1"):')
    cold = _run(root, h)
    assert cold["stats"]["stored"] == 2 and cold["targets"]["SynMade_v1"]["value"] == [2]
    assert "targets.py#_model_roots:Dup_v1" in _entry(root, "SynMade_v1")["reads"]["units"]
    _edit(root, "targets.py", "minus.make(False)", "minus.make(True)")
    assert _run(root, h, cache="fresh")["targets"]["SynMade_v1"]["value"] == [0xFFFE]
    warm = _run(root, h)
    assert "SynMade_v1" not in warm["hits"], (
        f"SynMade_v1 reused its entry (value {warm['targets']['SynMade_v1']['value']}) where a fresh run computes [65534]")
```

A note on the harness: the fresh caches sit beside the tree, not inside it. A cache directory inside the synthetic tree is
untracked and unignored, so it changes a listing that every target holds, and the tests then pass spuriously.
