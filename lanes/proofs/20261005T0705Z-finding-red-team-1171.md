## What I checked

- `test_evaluation` `INTEGRATIONS = {"verity_vllm"}`. The new predicate is a strict superset of the old one: a kernel is
  core unless its module's top-level package is exactly `verity_vllm`. It used to be core only when that package was
  exactly `verity`. The match is `partition(".")[0]` equality, not a prefix. Probes registering fake kernels from
  `verity_vllm_extra`, `verity_vllmx`, `verity_pouw.kernels`, `verity.ml.kernels` and `tests.fake` all make the test fail.
  Only `verity_vllm.k` is exempt. A key with one `verity_vllm` variant and one protocol variant also fails, because of
  `any(...)`. No kernel escapes that didn't before, and protocol kernels no longer do.
- `tools_registry.locate`, `from_tree` and `former_modules`, with `moves.json` empty today. `former_modules` returns
  `[]`, so `locate` is exactly the old check (`<module>.py` or `<module>/__init__.py`), and `from_tree` calls the old
  `_from_file` on the same pair. Behaviour on today's trees is unchanged. With moves, the current module is tried first;
  the move history is a fallback that only turns "no declaration" into "a declaration". For each caller:
  - `merge.declaration` feeds `required_steps`, `produced` and `declared_command`. `None` there was already the loosest
    case (no steps required, no kinds and no command). Finding a former declaration can only add requirements.
  - `remote.tool_preflight` used to skip, or refuse if asked, when the module was absent. It now runs the former
    declaration's preflight. When the file exists but can't be read, it still raises `PreflightFailed`.
  - `canary` still refuses without the `.py`.
  - `after_land` behaves as before.
  - A prefix false match (`tools.agreex` against `tools/agree/`) is prevented by the `+ "/"` check, and the
    longest-`new`-first ordering handles nested renames.
- `merge.py` and `remote.py` only swap the inline `REGISTRY…rpartition` plus `_from_file` for `locate` and `from_tree`.
  Nothing in grants (`queue.Rules`), the stale-head check, `old_history`, `unready`, `passing` or the
  exact-commit-and-tree rule changed.
- `frozen.path` now raises `FileNotFoundError` on a missing path. I fetched the frozen evidence: all 18 literal keys
  resolve, including the ledger directory with 50 `.jsonl` files. Every `frozen.path`, `frozen_dir()` and `frozen.root()`
  caller in the tree uses one of them. `reprice_v2.py`'s and `anchor_a100/report.py`'s `a.X or frozen.path(...)` are
  short-circuited when the flag is given, and `gkr/tensor/fused/bench.py` wraps its call in `except Exception`. Nothing
  that worked fails.
- `test_gate_paths.py` and `anchors.py` pass on the merged tree with the newer main (`a592a5567`), so I found nothing that
  would block the move wrongly.

## Non-blocking notes for the author

1. A broken `moves.json` makes `research merge` read the target's declaration as none. `locate` builds
   `(module, *former_modules(module))` eagerly, so `moves.json` is parsed even when the current module exists.
   `merge.declaration` catches every exception. With a malformed file, `declaration(repo, "check")` is `None` on today's
   tree (shown in the art). `required_steps` then returns `{}` (no `lean-agreement` requirement), and `produced` and
   `declared_command` come back empty. Two gates catch this before it lands:
   - `test_store_prov` parses the shipped file, so `check` fails;
   - `remote.tool_preflight` calls `locate` outside its `try`, so every `research run --tool` with a shipped tree raises.

   The gap: an entry whose `paths` values aren't strings passes the test's `isinstance(m["paths"], dict)` but raises in
   `former_modules`. Smallest fix: in `locate`, return the current module when it exists before calling `former_modules`.
   Optionally, also check in `test_store_prov` that every key and value in the shipped `paths` is a `str`.
2. In `former_modules`, two old paths renamed onto one new path (`{"a/": "m/", "b/": "m/"}`) yield only the first in dict
   order. A swap move (a↔b) resolves to the current path's file, which then holds the other tool. Neither can happen in a
   layout move that renames one-to-one, and `REGISTRY` is rewritten by the move.
3. The pre-existing pattern of treating an unreadable declaration as "no requirements" in `required_steps` fails open.
   It is older than this PR, and this PR doesn't widen it beyond note 1.
