## #1428 at `1ce9a45cc` (`cursor/vbridge-header-cap-95d4`, off `main` `e7b5caa89`): grant

- **The theorems say what the body says.**
  - `kLogOf_ok`: `kLogOf mj = .ok k ↔ J.nat mj "k_log" ctx = .ok k ∧ k ≤ 27`.
  - `lookup_index_test`: `(n != log2 size || 2^n != size) = (2^n != size)`. At runtime `||` short-circuits, so `2^n` is
    computed only when `n = log2 size`.
  - So the new `parse` accepts exactly what the old one accepted with `k_log ≤ 27`, and refuses the rest.
- **Every accepting path refused `c.kLog > 27` after `parse` already.**
  - `Stmt.setupH` refuses it at `HmRow.lean:1326`, unconditionally after `parse`. `Stmt.setupHidden` refuses it at
    `HmRow.lean:1876`, after `HmOut.parse`, which calls `HmRow.parse` first.
  - `Stmt.setupTables` reaches one of the two for every table. With `count ≤ 1` it calls `setup` directly. With
    `count ≥ 2` and no draw, it runs `parse` and `loadPublic` for `n`, then calls `setupH`/`setupHidden` for each table.
  - `FlockVerify`'s `verify`/`statement` reach `parse` only through these. `Stmt.setup` (BLAKE3) uses `Circuit.parse`
    and is untouched. `FlockRows` does not use `HmRow`.
  - So I found no accepting path that misses the refusal. The only callers that parse without `setupH` are
    `region-words` (`FlockVerify.lean:488`) and `typed-expand` (`:589`), the two diagnostics the body names; they are
    the only change in behaviour.
- **One-theorem ruling.** The fit is good: the set of accepted files did not grow, no proof file changed, and no
  guarantee statement changed.
- **`slot_log` needs no new refusal.** `check` refuses `slot_log < 7 || slot_log > k_log` at `HmRow.lean:312`, before
  `2 ^ slot_log` on lines 313–317. `Range.start` is computed only on use.
- **No other power in `check` or `parse` comes from an unbounded META number.**
  - `nextPow2 count` and `2 ^ unitLog` (`max 7 (log2ceil useful)`) grow only linearly in the file's own digits.
  - `ZK`'s `mask_log` reaches only a string.
- **The test (`8fd8c89cf`) and the refusal reasons are right.** The unedited RoPE circuit is accepted. The `k_log`
  file and the lookup file each exit 1 with the reason asserted.
- **Lock.** The verifier's lock is byte-identical to `main`'s. `verity/Security`'s lock changes only in
  `Flock.HmRow`: `parse` changed, `MAX_K_LOG` and `kLogOf` are new (128 to 130 definitions), and its 280 readers are the
  same. 1705 guarantees, none changed.
- **Audit `r20261007-003928-c8c2`.** It ran on `8fd8c89cf`; `8fd8c89cf..1ce9a45cc` is `PROTOCOL.md` and the lock only.
  - The verifier report and the Proofs report were on hand. The Security report was evicted; I fetched it as
    `art:354bbc1f281f1d2b2063534cfce78eb6665d331f7a8344976a0e708695923661`.
  - All three packages show 0 failures, axioms `propext`, `Classical.choice` and `Quot.sound` only, and a replay:
    verifier 5502 replayed, Security 6879, Proofs 58322.
  - Its guarantees and reads equal `1ce9a45cc`'s locks.
- **With #1391 (`f76770e48`).** I made a trial merge in a scratch worktree with the driver applied.
  - `HmRow.lean`, `PROTOCOL.md` and the test file merge cleanly. The merged `parse` holds `kLogOf`, then `check`, then
    `RecOpen.check`.
  - The lock driver refuses: `reads[Flock.HmRow].definitions[Flock.HmRow.parse]` changed on both sides. So whichever
    lands second must run `audit.py --update` on the merged tree for `verity/Security`. That re-records `Flock.HmRow`'s
    `parse` digest, which then holds both changes, and the group digest.
  - No proof refers to the `k_log` read, and #1391's proof edits (12 lines) don't touch it, so I expect the merged
    Proofs to build. I did not build them.
- **The report-only findings are no worse than the body says. Both fail closed.**
  - `Typed.read`'s `liveOk` calls `Array.replicate n`. The Lean 4.34 runtime sizes that with
    `lean_usize_mul_checked`, so a huge `n` panics; it cannot wrap. Otherwise allocation fails; either way the process
    exits.
  - `Circuit.checkLayout` computes `nextPow2 count * 2 ^ slot_log` and `2 ^ k_log` before any bound. Past 2^32 − 1
    that hits `Nat.pow`'s panic; below it, a large span runs out of memory. This is availability only.
  - A third site of the same kind, not in the body. Seen by reading the code, not run. When the unit returns its own
    outputs (`!tailOut`), `HmRow.check` allocates `Array.replicate c.outWords` at `HmRow.lean:404`. `outWords` is the
    sum of META `out_ports`' word counts, which `parse` reads with `J.asNat` and does not bound. A huge word count makes
    the verifier run out of memory before any refusal. It fails closed and is not a power, so the body's claim about
    powers stands.
