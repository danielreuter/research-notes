# Addendum to `20260929T0050Z-handoff-from-pous-pouw-sampled-proofs-questions`: recommended layout and three more questions

Daniel clarified at 00:49Z that the two-stage audit he means uses all three steps: serving commits only replay-unit I/O;
drawn replay units are replayed and their interiors committed; then some of their proof units are drawn for proofs.
bc-75d1b678 now recommends this layout:

- **Replay unit: a row block**, 16 activation rows by all outputs of one linear call. At serving, each row block commits
  y plus one Merkle root over its tiles' per-tile digests.
- **Interiors:** after the RU draw, the prover replays each drawn row block and commits its tiles' digests, which must
  hash to that root.
- **Proof units: tiles.** One tile per drawn row block is drawn and recomputed by the verifier.
- **Cost at 0.1% and 8192³:** about 4,600 row blocks and 4,600 tiles; about 2 ms of GPU replay per drawn row block
  (about 9 GPU-seconds per window) and about 20 CPU-seconds of verification. Retention is about 1.1 KB/token of roots,
  since replay regenerates the digests.
- **Hinges on question 7.** Under today's per-RU profile (1 − p·k/n_v) this layout is 512× worse, and tile = RU = proof
  unit wins instead.

**Changes to the first six:** question 2's second half (skipping the interiors step) no longer arises, since this layout
uses steps 3 and 4; question 5 now concerns only A rows, as the tile digests are interiors regenerated by the protocol's
own replay. The design also needs, not yet in the repo: the audit driver, the interiors step and second draw, the
root-match check, and the tile-counting profile, besides the RU class at p < 1 and the beacon-keyed RU draw.

## Questions

7. **Pinned interiors: may the profile count proof units?** *(addendum)*
   - In layout B, each row block's committed output includes a Merkle root over its tiles' digests. The interiors
     committed after the RU draw must match that root, and each tile's inputs (A rows, weights, derived noise) are
     committed at serving. So whether a tile is correct is fixed before the first draw.
   - `IntegrityProfile` allows a profile of several levels when "its checked level is committed before the first draw
     (… two-stage with every intermediate committed up front)". Here that would be Bernoulli(p) over row blocks and
     Subset(k) over tiles, counting wrong tiles.
   - May a two-stage audit emit that profile when its interiors are pinned this way? `TwoStageLaw.profile` today emits
     only the per-RU form, 1 − p·k/n_v, which would make layout B n_v/k times worse (§3.3).
8. **A replay unit whose output commits to its own interiors.** *(addendum)* Does the two-stage lifecycle support an RU
   output that is a root over some of its interior values, with step 3 checking that the committed interiors hash to it?
   Is that a leaf layout `vllm-v1` would add, and whose check is it (the protocol's, or the consumer's)?
9. **k RUs, or each RU with probability p?** *(addendum)* Daniel's description draws k RUs. `law.py` draws each RU
   independently with probability p (`select_replay_units`), and `IntegrityProfile` allows a fixed-size `Subset` only at
   the checked level. Which is intended? This design assumes the repo's Bernoulli form; a fixed count changes only the
   constants.
