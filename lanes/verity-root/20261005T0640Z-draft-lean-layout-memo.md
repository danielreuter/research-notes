# Where the Lean goes after the move: the decision memo (for Daniel, 5 Oct, by 5:00 AM PDT)

Tonight's move doesn't depend on this. It lands at 7:00 AM PDT as planned. This memo is about the next layout, the one
your 05:38Z rulings (locked points 1 to 7, `note:20261004T2058Z-draft-repo-organization-principles`) point at.

## The question

Where do each component's Lean programs, the security statements (assumptions, with the model inside them, and
guarantees) and the proofs live? Two candidates survived the evidence:

- **C, the ruled target:** `verity/<component>/lean/` holds each component's programs, with no dependencies (one Lake
  package, a library per component). `Security/Assumptions/` and `Security/Guarantees/` hold the trusted statements in
  one package on Mathlib. `Security/Proofs/` is its own package on Mathlib and ArkLib. Paths under `Security/` mirror
  the components, and a statement attaches to a program by importing its module and naming the constant, which the
  audit lock records.
- **T, today's directories with the Lake packages split:** every component keeps its Lean where it is (`Protocol`,
  `Assumptions`, `Guarantees` and `SecurityProofs` side by side). The packages split without any file moving: one for
  programs, one for statements and one for proofs, each picking its modules by source directory and roots.

Two others lost: statements inline in each component with one shared proofs directory (A), and a separate `lean/` tree
with verifier, specs and proofs packages (B). C ties A and beats B (63 to 0 PRs needing fewer directories), so they
aren't discussed further.

## The evidence

Four workers ran overnight: co-change and Lake (bc-e529d785), two run-model drafts in Lean (bc-03e91581 on
`cursor/run-model-draft-c3b2`, bc-c7b00243 on `cursor/run-model-draft-7bd6`), and a Lean module inventory (bc-8a03b032,
pending).

**Co-change (all 15 days of history, 2026-09-21 to 10-05, during heavy layout churn).** Of 170
PRs that touch Lean, T keeps 87% in one directory and C keeps 46%. Flock is most of them (133). For protocol PRs
without flock (37 PRs; GitHub's 51 and the 227 commits agree on direction), T keeps 89% in one directory and C keeps 3
to 8%: a protocol PR edits its program, its statement and its proof together, so under C it spans three mirrored trees
plus the component (3.2 directories on average). Protocol specs change with their proofs in 28 of 29 PRs.

**Lake.** Both layouts get the same gains, because the gains come from the package split, not the directories:
- the verifier builds with no dependencies and fetches nothing;
- Mathlib roots drop from seven (about 56 GB per checkout) to two (16 GB, 8.5 GB with a shared package directory);
- with statements and proofs as separate roots, the statements' workspace holds no ArkLib, so a statement importing
  ArkLib fails to build. The trust rule then holds at build time, not only in the audit.

Module names are global in Lake and duplicates are silently accepted (a toy build compiled the wrong file with no
warning). Either layout needs a test that every package's module roots are disjoint. That test is no-regret and is
being added now (see "Started without waiting").

**The run model.** Both drafts compose the whole run in Lean (locked point 4), and both put it in three layers:
programs with no Mathlib, statements on Mathlib without ArkLib, proofs on ArkLib. That is C's shape. The run's programs
cross components (the send gate runs C-Flock's `Statement.verify`; the coin server and the proxy share hm96), so the
run is a component of its own under either layout. Both drafts conclude the security statements belong together,
apart from the programs, because the composition theorem is stated over party programs from several components.

**What only C gives.** A file's path says its tier. `Security/Assumptions` plus `Security/Guarantees` is the whole
trusted text, one tree that can be listed and read. Under T, a statement and its proof sit side by side and are told
apart only by module names, lakefile roots and the guard.

## Recommendation

Do T's package split first, then move to C.

1. **Now, no-regret under both:** the namespace guard; the Lake split into programs, statements and proofs packages
   with no file moving; and a per-module audit cache, since `check` re-audits a whole package on any change (45 to 70
   minutes cold for soundness alone), which a single statements package would make worse. These get every measured
   Lake gain.
2. **Then C's directory move,** generated by `tools/move/layout.py` like tonight's, from the Lean inventory's map.

Why C over T, against the co-change numbers. Co-change counts directories, which costs little when paths mirror and
most PRs are written by agents. Your locked point 5 ("security proofs live apart from specs") and your 05:45Z proposal
both ask for the separation C makes visible. In a verification project, the trusted text an outside reviewer reads is
the product, and C makes it a tree rather than a convention. The cost is real: protocol work spans three trees, and a
statement no longer sits next to its proof. If you'd rather keep related code together, T after step 1 has every
measured gain and only lacks path-says-tier.

## What needs your call

1. **C or T.** Recommendation: C, after step 1.
2. **The 2026-10-03 ruling (card `d9eb2f28`): no package requires both a protocol and a backend.** The run's programs
   call C-Flock's verifier while its statements cite protocols, so locked point 4 can't be met under that ruling.
   Recommendation: relax it for the run's own Lean only. Protocols still import no backend.
3. **The extraction and the simulator move into `Security/Assumptions`.** They are trusted text, since a weak one makes
   the soundness guarantee vacuous, but today they sit behind ArkLib (`ZkOuter.layer`, `wmsg`, the Goldreich–Kahan
   finder). Recommendation: move them, so a guarantee can be read without ArkLib.
4. **`Security/` inside `verity/` or beside it.** Recommendation: inside, as `verity/Security/`, since you ruled that
   `verity/` is the whole system.
5. **Lean drives Python.** A toy audit (2^10 rows, a quarter wrong, 16 drawn, about 1% acceptance expected) accepted 0
   of 50 runs with Lean driving and 0 of 50 with an honest Python driver, but 20 of 20 with a Python driver that reruns
   the draw until it misses. Lean driving removes the coin-server assumption and two custody ZK assumptions, for 9.4 µs
   median per small request (0.35 ms at p99.9, so PoUS's 0.85 ms timing loop owns its socket and clock in Lean and is
   measured on a node before it moves). Recommendation: yes, phased one assumption at a time as the draft orders it.

Settled unless you object: "judge" is not a concept (both drafts agree with you; the deciding code is library functions
the party programs call, and the Glossary has no entry to retire). Engineering calls left to the owners: C-Flock's
soundness package has its own `Game` type, separate from core's (proofs moves it onto core's or adds a transport).
