## Findings and `research` papercuts
1. **A Commit that fails with a published verdict is classed `UNKNOWN_EXIT`** ("exit status 12 with no structured checker
   record", state `failed`). #67 `fb7c` published verdict `outcome: FAIL`; #57 `8cb4` is the same. So anything that keys on
   `state == done` misses it. The lane's chainer did, and never logged or stopped #57, #67 or #23 `eb64`, which made `chain.out`
   look like those rows were still running.
2. **`research pods drain` names the wrong failing leg.** It printed "attempt manifest not on the remote" for `d49b`, `db20`,
   `5647` and `8cb4`. `data preserved` showed the manifest on the remote; the real failure was the labels leg (laptop-only
   assertions).
3. **Pod-side PRESERVED ≠ the laptop's gate.** Labels asserted in the laptop store are invisible to a pod-side `data push` or
   `preserved`, so `ppush` said PRESERVED while the laptop drain refused. For a non-attempt artifact there is no scoped CLI to push
   only its labels:
   - `data push art:…` re-verifies every blob (259k for `f44e`);
   - `labels-sync --push-only` is store-wide.

   I used `labels_sync.push_targets` from a small laptop one-liner.
4. **Head-mode `data preserved` reads back every multipart blob.** For a 55 GB tree on a slow host that is hours, longer than the
   credential it runs with. `--mode recorded` answers instantly from the put's own verification. A "HEAD + multipart-ETag only"
   mode would fit this case.
5. **Credential expiry mid-close-out.** The lane's `cred.json` (7 h TTL) expired at 04:09:39Z and is baked into every script and
   job. I minted a fresh one with `data mint-credential --ttl 5h --via local`, sourcing `~/.config/verity/r2.env` in a subshell;
   it is valid until 08:49Z, and the old one is kept as `cred.0409Z.json`. The #57 fix lane can use it. Without the parent key in
   the environment, the default `--via auto` fails with a misleading "--via api needs CLOUDFLARE_API_TOKEN".
6. **Drain doesn't remove the machine entry.** `machines.toml` kept five pods the previous owner had already terminated.
7. **Host RAM on H100 rows.** #73 Commit and #74 Match each needed more than 233 GiB of host memory (the admission estimate was 211
   GiB, from uncalibrated qwen3-4b coefficients), which forced 2xH100 pods. #23's Commit ran at ~233 GiB anon+shmem against an
   advisory 327 GiB. Its log shows the planner calibration entry as "measured 0 MiB (None)", so no calibration was recorded.
8. The #23 Build harness table was lost with vyv-sw-23, because harness outputs were not stored (from the 00:00Z note).
9. Agent-shell papercut, not `research`: `nohup … &` jobs died silently with empty output, so I ran pushes in the foreground.
